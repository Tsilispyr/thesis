# `ai_backend/` - Training, Evaluation & Visualization Script Methodology

**Purpose of this document**: explains the *scripts that orchestrate* training/evaluation/plotting (as opposed to `ai_backend/models/ANALYSIS.md`, which covers the model architectures themselves, and `ai_backend/data_processing/ANALYSIS.md`, which covers the data pipeline). The question this file answers is: given correct data and a correct architecture, how are they actually trained, measured, and turned into a figure - and why do these scripts work the way they do, not some simpler way.

---

## `train.py` - supervised baseline trainer, and why early stopping was added

`train_model(sources, num_epochs, normalize, early_stopping_patience, min_epochs)` is the from-scratch supervised trainer (no SSL) - loads data via `dataset_parser`, builds `DeadReckoningLSTM`, trains with `Adam(lr=0.001, weight_decay=1e-4)` + `MSELoss`.

**Why early stopping + `ReduceLROnPlateau`, and why now**: the docstring states the reason directly (`train.py:22-27`) - once the leakage bugs described in `ai_backend/data_processing/ANALYSIS.md` were fixed, the *honest* validation curve was found to bottom out around epoch 3 and rise afterward. Before that fix, this didn't matter because the leaked numbers looked good regardless of epoch count - a fixed epoch budget silently hid overfitting. Early stopping was adapted from a pattern found in the user's own MSc Deep Learning coursework (`D:\ΠΜΣ\Βαθιά Μάθηση\Εργασίες εξαμήνου\2η Άσκηση\25118\25118.py`, per `AI_RECOVERY_EXECUTION_PLAN.md` §8) rather than written from scratch - patience-based (`epochs_since_best >= early_stopping_patience`, gated by a `min_epochs` floor so it can't trigger absurdly early), with the best `state_dict` deep-copied and restored at the end (`train.py:83-90, 103-104`) so the *saved* model is the best-validation checkpoint, not simply the last epoch trained. `ReduceLROnPlateau(factor=0.5, patience=2)` sits alongside it - a shorter-patience learning-rate decay that fires before the longer-patience stopping criterion does, giving the optimizer a chance to find a better plateau before giving up entirely.

**Why this exact loop shape reappears in `ssl_pretext.py`**: `models/ANALYSIS.md` documents that `ssl_pretext.py::_run_early_stopped()` is a near-identical extraction of this same loop, generalized to accept an `epoch_fn` so both SSL stages share one implementation. This duplication-then-consolidation is deliberate - `train.py` was written and validated first (on the simpler from-scratch case), and only once its stopping discipline was trusted was it factored out for reuse, rather than designing a shared abstraction speculatively before either concrete case existed.

**CLI defaults**: `--epochs 30 --patience 5`, sources default to `['imu']` (not `nav`, which is flagged deprecated directly in the `--sources` help text). Saves `dr_lstm_{tag}.pth`, both scalers, and `history_{tag}.json` - the last of which is what `visualize_training.py` consumes.

## `evaluate_trajectory.py` - why chained reconstruction, not windowed MSE

This is the file that turns "val loss = 0.72" into "26.3 metres off after 12.5 seconds" - arguably the most thesis-relevant methodological choice in the whole project, so it's worth stating precisely why it exists as a *separate* evaluation path rather than just reading numbers off `history_*.json`.

**The problem with windowed MSE alone**: every training script reports loss computed independently per 10-step window, in normalized (scaled) space. That number answers "how good is one prediction, in isolation, in scaler-units" - it does not answer "if I actually flew using this model's output, continuously, for N seconds, how far off the ground would I end up in metres." Those are different questions, and dead reckoning is specifically a task where the second one is what matters (the whole point is compounding drift over time when GPS is gone).

**The mechanism (`reconstruct_lstm()`, `evaluate_trajectory.py:49-70`)**: starting from the true position at the end of the first window (`pos = true_pos[WINDOW_SIZE-1].copy()`, an honest anchor - not the model's own output, so early error isn't artificially zeroed), each subsequent step (a) scales the next 10-step feature window with the *training-fitted* `scaler_X` (never re-fit here - same train/val discipline as `dataset_parser.py`), (b) runs the model, (c) inverse-transforms the predicted delta back to metres via `scaler_y`, and (d) **adds it to the running position** (`pos = pos + delta`, line 68) rather than resetting to ground truth each step. This last point is what makes it "chained" - errors compound exactly as they would in real deployment, because nothing resets the estimate back onto the true path between steps.

**The two baselines, from one class (`reconstruct_filter()`, lines 73-97)**: rather than write a second bespoke "naive integration" implementation, pure inertial integration is obtained by running the *same* `DeadReckoningEKF` with `use_baro=False` - i.e., the identical process model, just never calling `update_baro()`. This is a deliberate economy: it guarantees the "why do we need any correction at all" baseline and the "classical-filter" baseline share the exact same integration code, so any difference between their curves in `error_over_time.png` is attributable purely to the barometer correction, not to two independently-written (and possibly subtly different) integrators.

**The held-out segment (`load_val_segment()`, lines 37-46)**: explicitly the *same* 80/20 sequential split boundary used everywhere else (`create_dead_reckoning_dataset`'s convention) - a real, contiguous 12.5-second (3000-sample @ 240Hz) tail segment of `imu_data.csv`'s validation portion, not a cherry-picked window and not synthetic data. Ground truth (`ground_truth()`, line 100-101) is simply the dataset's own recorded position for that segment.

**Separation of computation from plotting**: `run()` saves a results JSON (`runs/trajectory_eval_{tag}.json`) rather than plotting directly - stated explicitly in the module docstring (lines 10-13) as deliberate, "so the (slower) reconstruction doesn't have to rerun every time a plot's styling changes." This is exactly what made the two chart-styling fix requests mid-project (rectangle-box style, table-text-color fixes) fast to iterate on - `visualize_trajectory.py` could be re-run against the existing JSON in seconds, with no retraining or re-inference involved.

## `visualize_trajectory.py` / `visualize_training.py` / `plot_style.py` - presentation layer

**`plot_style.py`** is the single source of truth for the fixed color-role palette the user specified as a standing directive (not a per-chart choice): `COLOR_REFERENCE` (cyan), `COLOR_PREDICTED` (magenta), `COLOR_GROUND_TRUTH` (black), `COLOR_EKF` (slate gray), `COLOR_PURE_INERTIAL` (muted coral), plus three sparingly-used accent colors (orange/red/green, added mid-project specifically "to catch the eye but not over the top clown coloring"). The key design point: these are **roles, not a cycled categorical palette** - every figure-generating script imports the same names rather than picking colors locally, so `COLOR_PREDICTED` means the same thing (the model's reconstruction) in every figure in the project, letting a reader learn the palette once. `style_axes()` centralizes title/label/grid/spine conventions (bold 12pt titles, muted gridlines at `alpha=0.3`, top/right spines hidden) so every chart shares one visual grammar.

**`visualize_trajectory.py`** consumes `evaluate_trajectory.py`'s JSON and produces the four Category-A/B figures documented figure-by-figure in `runs/figures_single_drone/ANALYSIS.md` (3D trajectory, XY/XZ projections, error-over-time). One notable fix applied mid-project: the initial 3D plot clipped its Z-axis label against the figure edge - resolved via explicit `figsize=(9,7)`, `ax.zaxis.labelpad=10`, and `fig.subplots_adjust(left=0.02,right=0.90,top=0.95,bottom=0.05)` in place of `bbox_inches='tight'`/`tight_layout()` (which don't reliably account for 3D label padding in matplotlib) - worth noting because it's a real, somewhat non-obvious matplotlib-3D gotcha rather than an arbitrary stylistic choice.

**`visualize_training.py`** consumes `history_*.json` files and produces the three training-curve figures plus the val-loss comparison bar chart (again, see `runs/figures_single_drone/ANALYSIS.md` for the per-figure interpretation). Each curve's "best epoch" is marked with a vertical dotted line and an annotation offset via `xytext=(10,18)` + `arrowprops` - fixed mid-project after the annotation was found overlapping the marked line itself in the initial version; the offset-plus-connecting-arrow is the standard matplotlib fix for label/data collision rather than a hand-tuned one-off number.

## `ml_pipeline.py` - the 12-step narrative dashboard (`runs/figures/`)

A separate, larger pipeline from the single-drone evaluation above - it exists to tell the *methodological* story end-to-end (dataset audit → cleaning → normalization → feature engineering → sequence windowing → four training runs A/B/C/D → comparison → summary dashboard) as 12 numbered figures, rather than to produce the trajectory-level result. It shares `dataset_parser.py`'s pipeline (no duplicate logic remains - an earlier version had its own `_build_sequences()` with the sequence-shuffle leakage bug described in `data_processing/ANALYSIS.md`; that duplicate has since been removed in favor of importing the same fixed functions everyone else uses).

**`_select_trustworthy_winner()`** (added most recently, `ml_pipeline.py`): both `step10_comparison()` and `step12_summary()` used to pick the "best" run via naive `min(runs, key=lambda r: r["final_val"])` - with no awareness that Runs A/B/D use the deprecated `nav` dataset, whose (now-understood-to-be-fake) position data can produce misleadingly low normalized losses for reasons that have nothing to do with real predictive quality (see `data_processing/ANALYSIS.md`'s Bug 2 for exactly this failure mode). The fix prefers `run_id == "C_imu_norm"` explicitly, falling back to the naive minimum only if that run is absent - so the dashboard's headline "winner" can never again be a nav-tainted run, even though nav is still included in the comparison for historical/completeness reasons.

Full figure-by-figure interpretation of the 12-step dashboard is in `runs/figures/ANALYSIS.md`, written against the fresh, leakage-fixed, correctly-attributed rerun of this script (not the earlier, since-superseded output).

## `eval_metrics.py` - path-recovery evaluation harness (status: paired with the un-upgraded RL prototype)

Two functions: `run_rule_based_eval()` (a trivial straight-line-to-target controller, 100 episodes, ~100% success by construction since it always moves directly toward a static target with no obstacles) and `run_rl_eval()` (loads `ppo_swarm_recovery.zip` if present and runs it against `SwarmRecoveryEnv`, same episode/step budget). This file evaluates exactly the `rl_path_recovery.py` prototype flagged in `models/ANALYSIS.md` as not-yet-upgraded (raw-coordinate state, undertrained at 10K timesteps) - its numbers (rule-based ~100% vs. RL ~28%, from the original audit) describe that prototype honestly, and will need to be regenerated once Phase 3's planned upgrade (state = reconstructed position + uncertainty, 500K-1M timesteps) lands; not rerun as part of this document's writing since no code in this file or `rl_path_recovery.py` changed this session.

## Summary: how a number becomes a figure, end to end

1. `dataset_parser.py` turns raw CSVs/`.ulg` logs into leakage-safe, unit-verified, windowed tensors.
2. `train.py` or `ssl_pretext.py` trains a model against those tensors with early stopping, saving `.pth` weights, scalers, and a `history_*.json`.
3. Either (a) `visualize_training.py` reads that JSON directly for a loss-curve figure, or (b) `evaluate_trajectory.py` loads the saved model+scalers, reconstructs a real chained trajectory against a held-out segment, and saves a `trajectory_eval_*.json`, which `visualize_trajectory.py` then turns into the 3D/projection/error figures.
4. `ml_pipeline.py` runs a separate, self-contained 12-step version of steps 1-2 end-to-end for the narrative dashboard, sharing the same underlying `dataset_parser` functions so its numbers are directly comparable to everything else in the project.

Every arrow in that chain was, at some point this session, the specific place a bug was found (leakage in step 1, overfitting invisible without step 2's early stopping, windowed-MSE being insufficient to judge real-world usefulness in step 3) - the scripts in this folder are shaped the way they are because of that history, not by upfront design.
