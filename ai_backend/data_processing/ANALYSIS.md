# `ai_backend/data_processing/` - Pipeline Methodology & the Bug-Fix Narrative

**Purpose of this document**: explain not just what this pipeline does today, but the sequence of real methodological bugs found in it and fixed over the course of this project - because *why* the pipeline looks the way it does now is inseparable from what went wrong before. This is the single most important folder for the thesis's "data integrity" claims, since every downstream model result depends on it.

---

## The central file: `dataset_parser.py`

This is the single source of truth for feature/target column definitions (`FEATURE_COLS`, 14 columns; `TARGET_COLS`, 3 columns; `INPUT_SIZE = 14`) and for turning raw CSVs/`.ulg` logs into normalized, windowed LSTM training tensors. Every other file in the project that touches training data (`train.py`, `ssl_pretext.py`, `ml_pipeline.py`, `evaluate_trajectory.py`) imports from here rather than redefining these constants - originally, the audit's top documentation-drift finding was that `FEATURE_COLS`/`INPUT_SIZE`/`DeadReckoningLSTM` were duplicated across 4+ files, which is exactly how `api/server.py` silently drifted out of sync with an 8-feature model that no longer matched a 14-feature pipeline. Consolidating to one importable source directly fixed that class of bug.

## Three real bugs, found and fixed in sequence, in this exact pipeline

These are presented in the order they were discovered, because each one was found *while investigating the previous one's fix* - a chain of "why is this number implausibly good/bad" that a thesis committee will want to see traced honestly, not summarized as "we cleaned the data."

### Bug 1 - Sequence-shuffle leakage

**What was wrong**: an earlier version of the windowing logic shuffled the overlapping sliding windows *before* splitting into train/val. Since adjacent windows share up to 9 of their 10 timesteps, this put near-duplicate samples on both sides of the split - the model was effectively being evaluated on data it had already almost-seen during training, producing artificially good validation numbers.

**The fix, as implemented in `create_dead_reckoning_dataset()` (`dataset_parser.py:371-434`)**: windows are built in strict temporal order and the split is a plain slice (`X[:split]`, `X[split:]`, `dataset_parser.py:412-414`) - **no shuffling of the windowed array, ever**. The docstring states the reasoning explicitly (lines 382-385): "Sequences are kept in temporal order and split sequentially (not shuffled) - shuffling overlapping sliding windows before a split leaks validation data into training, since adjacent windows share most of their timesteps." This is now a structural property of the function, not a one-off fix that could silently regress - anyone editing this function sees the warning immediately above the split line.

### Bug 2 - Domain-shift scaler contamination (nav + imu concatenation)

**What was wrong**: `uav_navigation_dataset.csv` ("nav") stores position as GPS degrees (`lat≈37.777°`); `imu_data.csv` ("imu") stores position as relative metres. Concatenating the two raw and taking a single `.diff()` across the nav→imu boundary produced one row with a delta of roughly `(-37.8, +122.4, -148)` - a target-space outlier around 1000x larger than a normal per-step delta (~0.01-0.05). Fitting a single `StandardScaler` over that combined array let one outlier inflate the fitted standard deviation several-fold, which artificially *shrank* the normalized error for all other rows - a val loss that looked implausibly good (0.0669) for the wrong reason, not because the model got better.

**The fix, now structural in the code**:
1. **Per-source delta computation, before any concatenation.** `load_and_clean_navigation_data()` converts nav's degree-scale lat/lon diffs to metres using an equirectangular approximation (`_M_PER_DEG_LAT = _M_PER_DEG_LON = 111_320.0`, `dataset_parser.py:33-34, 76-80`) so its `delta_lat`/`delta_lon`/`delta_alt` are physically comparable to imu's (which are already plain metre diffs, `load_and_clean_imu_data()` lines 108-119). Each loader computes its own deltas independently - a delta is never computed *across* a source boundary in the first place.
2. **`_src_id` boundary-aware windowing.** `load_combined_dataset()` tags every row with a `_src_id` (`dataset_parser.py:341,348,215`), and `create_dead_reckoning_dataset()`'s window-building loop explicitly skips any window whose start and end row belong to different `_src_id`s (`dataset_parser.py:403-405`) - so even with per-source deltas already correct, a *window* still can't accidentally straddle two physically unrelated recordings (this matters even more for the 6 independent PX4 flights, each with its own `_src_id = 1000+i`).
3. **`verify_unit_consistency()` as a standing precondition, not a one-time patch.** Rather than trusting future edits to remember "convert units before combining," `load_combined_dataset()` calls `verify_unit_consistency(named_frames)` (`dataset_parser.py:362`) whenever 2+ sources are requested - it computes per-source mean/std for every shared `FEATURE_COLS`/`TARGET_COLS` column and raises `ValueError` if any cross-source std ratio exceeds `UNIT_MISMATCH_THRESHOLD = 3.0` (`dataset_parser.py:227-306`), unless the specific `(source_a, source_b, column)` triple has been explicitly passed in as `reconciled` (i.e., a human verified and handled it, not silenced it by raising the threshold globally). This one function is a direct, generalized response to *three* separate incidents this project hit: this nav/imu domain shift, the scaler-fit-order bug below, and the still-open imu/px4 gyro-unit mismatch (rad/s vs. an unverified scale, ~57x apart if naively combined) - turning "remember to check units" from a documentation reminder into code that fails loudly.

Because `nav` is retained in the codebase only to reproduce this historical negative result (see Bug 3's sibling finding below - nav's position data was later found to be physically impossible, not just differently-scaled), `load_combined_dataset()` prints an explicit deprecation warning whenever `'nav'` is requested (`dataset_parser.py:336-338`), and the module's own `__main__` block (`dataset_parser.py:437-459`) demonstrates the gate actively *blocking* `('nav','imu')` and `('imu','px4')` as an executable proof the check works, not just a claim in a docstring.

### Bug 3 - Scaler fit-before-split leakage

**What was wrong**: even after Bugs 1 and 2 were fixed, both `create_dead_reckoning_dataset()` and (at the time) `ml_pipeline.py`'s own duplicate windowing logic called `StandardScaler().fit_transform()` on the **entire** feature/target array before the train/val split - meaning the scaler's fitted mean/std for every reported run, including the newly-"honest" 0.7466 baseline, were computed partly from validation-set statistics. A milder leak than Bug 1, but the same category of error, and it was found specifically by cross-referencing this codebase's scaler discipline against a rule stated explicitly in the user's own MSc Data-Mining coursework (`AI_RECOVERY_EXECUTION_PLAN.md` §8): fit any normalizer on the train split only, then transform (never re-fit) the test/val split.

**The fix, as implemented (`dataset_parser.py:411-427`)**: the split happens first (line 412-414); `scaler_X`/`scaler_y` are then constructed and `.fit_transform()`-ed **only on `X_train`/`y_train`** (lines 421-422, 425-426); `X_val`/`y_val` are transformed with `.transform()` using those train-fitted parameters (lines 423, 427) - never re-fit. This ordering is now baked into the one function every training script calls, so there is no remaining code path that can regress this.

## The fourth finding - not a code bug, a data-integrity finding: `uav_navigation_dataset.csv` is not real

Independently of the three bugs above, direct inspection of `uav_navigation_dataset.csv` ("nav") found its position data to be **physically impossible**: a single timestep implies roughly 1000-2200 m of movement while the dataset's own `speed` column simultaneously reports 7-30 m/s for that same timestep - inconsistent by roughly two orders of magnitude, the signature of synthetic/randomly-generated position data rather than a real or even a physically-simulated trajectory. Per the user's explicit instruction at the time ("dig in further but act as like there is a problem and not a solution, don't try and justify the wrong data"), this was not patched, adjusted, or explained away - `nav` was formally deprecated (`load_combined_dataset()`'s runtime warning, `dataset_parser.py:320-325, 336-338`) and is kept loadable *only* to reproduce the historical negative result in the documentation, never for new work.

**The response**: rather than continue working with synthetic data of unknown/questionable provenance, real hardware flight logs were sourced from the public PX4 Flight Review database (`https://review.px4.io`, CC-BY, Dronecode Foundation) - `download_px4_logs.py` and `load_and_clean_px4_data()` (below) are the direct result of that decision.

## `load_and_clean_px4_data()` - real-hardware data integration

Parses `.ulg` flight logs via `pyulog`, extracting five topics (`sensor_combined`, `vehicle_attitude`, `sensor_mag`, `vehicle_local_position`, `actuator_outputs`) and aligning them onto `sensor_combined`'s timeline via `pd.merge_asof` - the standard technique for combining several sensor topics that each sample at different, not-perfectly-synchronized rates (`dataset_parser.py:161-192`). Notable, documented design decisions:
- **Position source is `vehicle_local_position`, not `sensor_gps`** - direct inspection of the first downloaded batch found `sensor_gps.latitude_deg` uniformly `0.0` (many public PX4 logs are indoor/optical-flow test flights with no real GPS fix), while `vehicle_local_position` (EKF2's fused local-position estimate, metres, NED frame) is populated regardless of position source (`dataset_parser.py:126-135`) - another instance of verifying an assumption against the actual data rather than trusting a column name.
- **Quaternion → Euler conversion** (`dataset_parser.py:197-200`) matches the same roll/pitch/yaw-in-degrees convention used everywhere else in `FEATURE_COLS`, so px4 rows are schema-compatible with imu rows even though the mismatch on gyro units (documented in the function's own docstring, lines 142-147) still blocks actually combining them under one scaler until reconciled.
- **Per-flight `_src_id = 1000 + i`** (line 215) - offset specifically chosen to never collide with `nav`'s `_src_id=0`/`imu`'s `_src_id=1`, so all three sources can in principle coexist in one combined frame's boundary-aware windowing once the remaining unit mismatch is resolved.

`download_px4_logs.py` documents its own selection logic directly in its docstring: filters the public log database for error-free (`num_logged_errors=0`), EKF2-estimated, Quadrotor flights of 120-600s duration, newest first, respecting the server's documented 6-second rate-limit convention (matching PX4's own official download tool) since this is a free service funded by the Dronecode Foundation.

## `flight_recorder.py` - closing the loop back into the simulation

A straightforward CSV writer (`FlightRecorder.record()`) that appends one row per UDP telemetry packet received from the Godot simulation, including `motor_0..motor_3` (flattened from the `motor_out` list) - this exists specifically because neither offline CSV (`uav_navigation_dataset.csv`, `imu_data.csv`) has a motor-thrust column at all, and the full "Connectivity Prediction" vision (reconstructing position from the *complete* sensor-fusion set: motor + baro + mag + IMU, not IMU alone) requires a dataset that doesn't exist yet. This is the mechanism by which the now-physically-real Godot telemetry (fixed in `drone_body.gd`, see `simulation/README.md`) becomes a genuinely new training corpus - flying the simulation through varied maneuvers with recording enabled is what will eventually populate the 4th benchmark source beyond (A) simulation-IMU, (B) real PX4, (C) fused.

## `osm_terrain_fetcher.py`

Not part of the ML training pipeline - fetches OpenStreetMap-derived terrain/road data for the simulation environment. Included in this folder for proximity to the other data-acquisition scripts, not because it feeds the dead-reckoning dataset.

## Why this narrative matters for the thesis

Every one of the three code bugs above shares the same shape: a plausible-looking, even *good-looking* validation number (leakage always makes things look better, never worse) that turned out to be measuring something other than what it claimed to measure. The methodological contribution worth writing up is not just "the final LSTM beats an EKF baseline" (see `runs/figures_single_drone/ANALYSIS.md`) - it's the discipline that got the numbers to a point where that comparison is actually trustworthy: temporal-order splitting, source-boundary-aware windowing, train-only scaler fitting, and a standing automated unit-consistency gate that turns "remember to check" into "cannot silently happen again."
