# Ablation Matrix Figures -- Figure-by-Figure Analysis

**Purpose of this document**: a thesis-ready walkthrough of every figure in this folder -- what it shows, what it means, what decision or finding it represents, and how it connects to `runs/ablation/cpu_run1/ANALYSIS.md`'s statistical findings (the point-estimate/CI table, the coefficient-of-variation finding, the "windowed vs chained" theme). Written to be liftable directly into a Results/Discussion chapter. It does not repeat that document's tables, it explains what the pictures behind those tables actually look like.

**Context**: this is the first time in the project the full 3-seed x 6-model + 2-baseline ablation matrix (`runs/ablation/cpu_run1/results.json`) gets a figure set of its own, rather than the single-run figures in `runs/figures_single_drone/` (LSTM-vs-EKF only) or the one summary bar chart in `ablation_matrix.png` (chained metric only, no per-model trajectory detail, no training-curve view of seed spread). All numbers below come from `ai_backend/models/history_*.json` (per-seed training histories), `runs/ablation/cpu_run1/results.json` (per-seed chained error), and this folder's own `trajectory_eval_ablation.json` (produced by `ai_backend/visualize_ablation.py`, same schema convention as `evaluate_trajectory.py`'s output).

## The representative-seed rule, stated explicitly

Six of the eight methods in this comparison are stochastic (LSTM, SSL-LSTM, Transformer, SSL-Transformer, RandomForest, GBT); each was retrained 3 times from different seeds. Four of the figures below (`trajectory_3d.png`, `trajectory_xy.png`, `trajectory_xz.png`, `error_over_time.png`) can only show one trajectory per model. Picking the **best**-performing seed for each model would silently cherry-pick 6 lucky runs and overstate every method's real accuracy simultaneously; picking the **worst** would do the opposite. Instead, every trajectory figure in this folder uses each model's **median-seed checkpoint**: the seed whose final chained error sits in the middle of that model's 3 seeds, computed programmatically in `visualize_ablation.py::median_seed_index()` from the same `per_seed` arrays `runs/ablation/cpu_run1/results.json` already contains, not chosen by eye. The six representative seeds this rule selected:

| Model | Representative seed | Final err [m] (this seed) | All 3 seeds' final err [m] |
|---|---|---|---|
| LSTM | seed 0 | 30.01 | 30.01, 29.48, 35.64 |
| SSL-LSTM | seed 0 | 36.87 | 36.87, 37.51, 31.92 |
| Transformer | seed 2 | 7.15 | 14.17, 3.22, **7.15** |
| SSL-Transformer | seed 0 | 13.22 | **13.22**, 11.15, 19.80 |
| RandomForest | seed 2 | 26.59 | 27.27, 26.19, **26.59** |
| GBT | seed 0 | 18.06 | **18.06**, 20.87, 17.27 |

Two things worth noting about this table on its own: (1) the representative seed is not always seed 0 -- Transformer's representative run is seed 2 and RandomForest's is seed 2, exactly because the rule is about final-error rank, not seed index, so it cannot be gamed by always picking the first run; (2) the spread visible in the "all 3 seeds" column previews the coefficient-of-variation finding below -- Transformer's own three numbers (14.17, 3.22, 7.15) span more than a factor of 4, while RandomForest's (27.27, 26.19, 26.59) barely move. EKF and Pure Inertial are deterministic (no barometer/process noise randomness across runs in `reconstruct_filter`), so they need no seed selection at all.

## Training curves -- `train_lstm.png`, `train_ssl_lstm_pretrain.png`, `train_ssl_lstm_finetune.png`, `train_transformer.png`, `train_ssl_transformer_pretrain.png`, `train_ssl_transformer_finetune.png`

**What they show, as a set**: each figure overlays all 3 seeds' train/validation curves for one training stage of one architecture, using the same color/linestyle roles as `visualize_training.py`'s single-seed version (train loss solid black, validation loss dotted slate gray) with seed identity carried by alpha (seed 0 at 0.9 opacity, seed 1 at 0.6, seed 2 at 0.4) rather than line style -- line style in this project is already reserved for the primary/predicted-vs-baseline/reference role (`plot_style.py`), and reusing it to distinguish seeds would collide with that established meaning, exactly what the project's own memory (`feedback_ai_recovery_graph_style.md`) says not to do.

**`train_lstm.png`**: three near-identical overfitting curves. Train loss falls from ~0.69 to 0.19-0.24 across all three seeds; validation loss for every seed plateaus almost immediately and never drops meaningfully below its starting value (best_val 0.7122, 0.7475, 0.7320 for seeds 0/1/2, early-stopping at epoch 1 for two of the three seeds and epoch 3 for the third). This is the same textbook-overfitting shape `runs/figures_single_drone/ANALYSIS.md` documented for the single earlier LSTM run, now confirmed to be a property of the architecture/data combination rather than one unlucky seed: all three independently-initialized, independently-shuffled runs land in the same 0.71-0.75 validation-loss band. The three dotted validation curves visibly interleave rather than clearly separate, which is itself informative -- it says the LSTM's plateau is a hard ceiling this data/architecture combination hits regardless of initialization, not a threshold a different seed could get lucky past.

**`train_ssl_lstm_pretrain.png`**: the pretext task (masked-timestep reconstruction) again shows the same healthy, no-overfitting shape across all three seeds that `runs/figures_single_drone/ANALYSIS.md` reported for the single earlier run -- train and validation loss track each other closely the whole way, falling smoothly from ~0.184-0.186 to a best validation loss of 0.1524-0.1542 across seeds (essentially identical across seeds, a striking contrast with the fine-tuning stage two figures later). Seeds 1 and 2 ran longer before early stopping (28 and 27 epochs vs. seed 0's 21) but converged to the same place, consistent with a well-posed pretext objective rather than one seed finding a shortcut the others missed.

**`train_ssl_lstm_finetune.png`**: fine-tuning from the pretrained encoder reproduces the from-scratch LSTM's plateau problem, seed for seed -- best validation loss 0.8176, 0.8163, 0.7923 for seeds 0/1/2, every one of them worse than every one of the from-scratch LSTM's three seeds (0.7122-0.7475) in the previous-but-one figure. This is the multi-seed confirmation of the single-run negative SSL result `runs/figures_single_drone/ANALYSIS.md` first reported: it is not one unlucky fine-tuning run, all three independently-pretrained-and-fine-tuned SSL-LSTM seeds land worse than all three from-scratch LSTM seeds on the windowed metric, with zero overlap between the two three-number sets.

**`train_transformer.png`**: this is the figure that puts a face on `runs/ablation/cpu_run1/ANALYSIS.md`'s headline reliability finding -- **the Transformer is the least consistent model in the whole matrix (168% relative variability, CI margin larger than the mean itself)**. Visually, this shows up exactly where it should: the three seeds' curves clearly separate rather than interleaving the way the LSTM's did, most visibly in the validation-loss (dotted) traces, which fan out into three distinguishable, non-overlapping bands by epoch 6-9 (best validation loss 0.3307, 0.3623, 0.4049 for seeds 0/1/2, versus the LSTM's much tighter 0.7122-0.7475 spread on a similarly-sized loss scale). Seed 2's curve sits visibly above the other two for the whole run, not just at the final epoch -- the instability is present throughout training, not merely a late-epoch fluke. This is the direct visual evidence behind the numeric CoV finding: a model whose three otherwise-identical training runs produce three visibly different validation-loss trajectories is a model whose single-run number should be read with real skepticism, exactly the practical read `runs/ablation/cpu_run1/ANALYSIS.md` recommends.

**`train_ssl_transformer_pretrain.png`**: like the LSTM's pretraining stage, this is clean and well-behaved across all three seeds (best validation loss 0.0172-0.0198, all three seeds reaching essentially the same low reconstruction loss, two of three running the full 30 epochs before the budget ended rather than early-stopping). The pretext task itself is not where the Transformer's instability comes from -- it appears specifically once the model is asked to solve the harder, less-constrained delta-position regression task.

**`train_ssl_transformer_finetune.png`**: fine-tuning from the pretrained Transformer encoder reaches best validation loss 0.3792, 0.3429, 0.3593 (seeds 0/1/2) -- a tighter three-seed spread than the from-scratch Transformer's own 0.3307-0.4049, and, unexpectedly, a slightly **better** mean (0.3605 vs. 0.3660). This is the first hint of the windowed-vs-chained disagreement the next section covers in full: on the windowed metric shown in this figure and the next, SSL pretraining looks like a (marginal, CI-overlapping) win for the Transformer, the opposite of the LSTM's clear-cut SSL loss two figures earlier.

**The RandomForest / GBT limitation, stated plainly**: neither model has a per-epoch training curve, and none is fabricated here. `RandomForestRegressor` and `HistGradientBoostingRegressor` are fit once per seed via `GridSearchCV` (hyperparameters tuned on seed 0, reused with only `random_state` varying for seeds 1-2, per `ablation_matrix.py::train_one_seed`'s documented rationale) -- there is no notion of "epoch" for either estimator, so `train_randomforest.png` / `train_gbt.png` do not exist and are not expected to. Their only fitting-process record is `history_rf_*.json` / `history_gbt_*.json`'s single `val_mse` + `best_params` per seed, which is exactly what `comparison_val_loss.png` below uses instead of a curve.

## `comparison_val_loss.png` -- Windowed Validation Loss by Model (3-seed 95% CI)

**What it shows**: one bar per stochastic model, mean windowed validation MSE loss across 3 seeds with a t-distribution 95% CI error bar (`ablation_matrix.py::confidence_interval()`, the same function, same clipping-at-zero rule, `ablation_matrix.png` already uses for the chained metric) -- LSTM 0.731 [0.687, 0.775], SSL-LSTM 0.809 [0.773, 0.844], Transformer 0.366 [0.274, 0.459], SSL-Transformer 0.361 [0.315, 0.406], RandomForest 0.664 [0.657, 0.670], GBT 0.355 [0.345, 0.365]. Deliberately styled to match `ablation_matrix.png` exactly (same `ABLATION_MODEL_COLORS` mapping, same bar/error-bar/grid/spine conventions, same figure width) so the two can be read side by side as two views of the same six models.

**What it means, read next to `ablation_matrix.png`'s chained metric -- do the two metrics agree?** Mostly, but not entirely, and the one disagreement is the interesting part. LSTM-family ranking agrees on both metrics: LSTM beats SSL-LSTM on windowed loss (0.731 vs 0.809) exactly as it does on chained final error (31.71 m vs 35.43 m) -- the SSL penalty is real and consistent whichever metric you read it from. GBT and RandomForest also agree directionally (GBT clearly better than RandomForest on both). **The Transformer family is where the two metrics disagree**: on windowed loss, SSL-Transformer (0.361) is marginally *better* than the from-scratch Transformer (0.366) -- their CIs overlap heavily, so this is not a strong claim, but the point estimate favors SSL. On the chained metric in `ablation_matrix.png`, the ranking flips hard: from-scratch Transformer (8.18 m) is clearly better than SSL-Transformer (14.72 m), a much larger relative gap than the windowed numbers would suggest. This is exactly the "windowed vs chained" theme `runs/figures_single_drone/ANALYSIS.md` and `ai_backend/models/ANALYSIS.md`'s RandomForest section both flagged before (a metric that looks fine, or even favorable, in isolation can still fail once errors compound) -- here it shows up as a **ranking reversal on close point estimates**, not just a magnitude discrepancy, and it is worth stating precisely: had this project stopped at the windowed metric alone, it would have reported SSL pretraining as a narrow win for the Transformer arm. The chained metric, the one this project has repeatedly established as the one that reflects real deployment behavior, says the opposite.

**RandomForest's windowed number, read carefully**: RandomForest's windowed loss (0.664) sits between the Transformer/GBT/SSL-Transformer cluster (~0.36) and the LSTM/SSL-LSTM cluster (~0.73-0.81) -- notably worse than GBT despite both being tree-based, consistent with `ai_backend/models/ANALYSIS.md`'s original single-run finding that RandomForest's windowed improvement over the LSTM did not reliably carry through to chained accuracy either (RandomForest chains to 26.68 m, barely better than the LSTM's 31.71 m, while GBT's much better windowed loss does carry through to a much better chained result, 18.73 m). Both instances point at the same underlying caution: a windowed-loss ranking is suggestive, not sufficient, evidence for a chained-accuracy claim.

## `trajectory_3d.png` / `trajectory_3d_top_performers.png` -- 3D Trajectory Reconstruction

**What they show**: the same real 12.5 s held-out spiral maneuver `runs/figures_single_drone/ANALYSIS.md` used, now with all 6 learned models' representative-seed reconstructions plus both classical baselines (EKF, Pure Inertial) in one figure -- solid lines for the 6 learned models, dotted for the 2 classical baselines, a black dot marking the shared start. `trajectory_3d.png` shows all 8 methods; `trajectory_3d_top_performers.png` restricts to the three strongest-ranked methods by chained final error (Transformer, GBT, SSL-Transformer, per `runs/ablation/cpu_run1/ANALYSIS.md`'s ranked table) plus both baselines, produced in addition to (never instead of) the full 8-series version.

**What it means**: the headline visual story repeats and sharpens the single-model finding from `runs/figures_single_drone/ANALYSIS.md` -- both classical baselines visibly launch away from the real spiral into a completely different region of 3D space (Pure Inertial climbing past 60 m altitude while the real flight stayed near 15-20 m), while all six learned models, regardless of architecture, stay in the same general volume as the ground truth. That is the qualitative floor every learned model clears; the *quantitative* differences among the six are what the reduced top-performers version isolates. In the full 8-series view the six learned paths visibly bunch together near the start of the maneuver, which is exactly why the reduced version exists: once the two order-of-magnitude-larger baseline excursions are removed, the top-performers view makes the Transformer's path (the tightest of the three shown) versus GBT's and SSL-Transformer's wider excursions into the second half of the spiral easier to compare directly than they are in the full view, where all three sit visually close to the LSTM/SSL-LSTM/RandomForest paths as well.

## `trajectory_xy.png` / `trajectory_xy_top_performers.png` -- Top-Down XY Path View

**What they show**: the same 8 (or top-3 + baselines) paths projected onto the horizontal plane -- per `runs/figures_single_drone/ANALYSIS.md`, this is the clearest single view of "how far off course" each method ends up, since it is not compressed by the comparatively small altitude variation.

**What it means**: this is the most information-dense figure in the set, and it makes the CI-overlap caution from `runs/ablation/cpu_run1/ANALYSIS.md` visible rather than abstract. The two baselines separate from everything else immediately and by a huge margin (Pure Inertial ends near +90 m / +80 m, off the right edge of the ground-truth spiral entirely). Among the six learned models, the picture is genuinely mixed, not a clean best-to-worst fan: the Transformer (green) and SSL-Transformer (brown) trace paths that visibly extend furthest into the lower-right, tracking more of the ground-truth spiral's southward loop than LSTM/SSL-LSTM/RandomForest (blue/purple/orange), which stay in a tighter cluster near the start and cut the loop short. GBT (red) sits in between, forming a small loop of its own that partially echoes the ground truth's spiral shape without matching its exact position. None of the six paths closes the loop the way the black ground-truth spiral does -- consistent with all six models' non-zero, non-trivial final chained error (7-37 m across the six representative seeds) even while all of them stay in the right general neighborhood. The top-performers version makes the Transformer's comparatively tighter path easier to see without the visual competition of the other three learned models and both baselines' dramatic excursions.

## `trajectory_xz.png` -- Elevation XZ Path View

**What it shows**: the same 8 paths projected onto the vertical plane, isolating altitude behavior from horizontal drift -- produced only in the full 8-series version, no reduced top-performers variant, because unlike the XY/3D views this projection is not visually cluttered even with all 8 series: altitude stays tightly bounded (roughly 8-20 m) across all six learned models and even the EKF, so the lines are visually separable without needing to remove any of them.

**What it means**: this figure reproduces, at 6x the model count, the single most robust finding `runs/figures_single_drone/ANALYSIS.md` reported for the LSTM/EKF pair -- altitude is the easy axis. All six learned models and the EKF stay within a roughly 10-20 m altitude band, visually close to the ground truth's own 12-19 m range, while only Pure Inertial (no barometer correction at all) drifts up past 60 m. This is the clearest evidence in this figure set that horizontal drift, not vertical drift, is where the six learned models actually differ from each other and from the ground truth -- the differences visible in `trajectory_xy.png` are not an artifact of a 3D view compressing a genuinely 3D disagreement, they are the real story, and altitude is comparatively a solved sub-problem for every method tried here, learned or classical, given even the EKF's single barometer correction.

## `error_over_time.png` -- Position Error Growth over Time (all 8 methods)

**What it shows**: the same Euclidean-error-vs-time construction as `runs/figures_single_drone/ANALYSIS.md`'s single most information-dense figure, now with 8 lines instead of 4 -- the two classical baselines (dotted) growing essentially linearly and without bound, and all six learned models (solid) staying bounded in a 0-48 m band across the full 12.5 s segment. Unlike the 3D/XY views, all 8 series stay visually separable here without needing a reduced version, since the classical baselines' near-linear drift and the learned models' bounded oscillation pull the lines apart as time progresses (per this project's own prediction in the original task scoping: this chart has "less of a risk" of clutter than the trajectory-shape views, confirmed by the rendered figure).

**What it means, precisely, reading the final-time values left to right by rank**: Transformer (7.15 m) and SSL-Transformer (13.22 m) end lowest, followed by GBT (18.06 m), RandomForest (26.59 m), LSTM (30.01 m), and SSL-LSTM (36.87 m) -- exactly the ranking `runs/ablation/cpu_run1/ANALYSIS.md`'s point-estimate table reports, since these are that table's own representative-seed numbers, now visible as full time series rather than single endpoint values. The time-series view adds something the endpoint table cannot: **all six learned curves share a visible common structure** -- a small error bump around 1 s, a dip back toward zero near 4-4.5 s (all six models' predicted position happens to re-cross the true position at roughly the same moment), then a shared, steep error ramp starting around 5.5-6.5 s that produces most of each model's final error, before partially recovering and re-stabilizing after roughly 9 s. This shared shape across all six independently-trained architectures strongly suggests the ramp corresponds to a genuinely harder stretch of the real maneuver (a tighter turn or a higher-dynamics segment of the spiral) that every model, regardless of architecture or training procedure, struggles with similarly -- a data-difficulty effect, not a per-model weakness. The two classical baselines show no such structure at all, just steady near-linear drift, because they have no learned sensitivity to the flight's actual dynamics to be disrupted by a harder segment in the first place -- which is itself the clearest visual argument in this whole figure set for why a purely physics-integrating baseline behaves so differently from every learned model tried, independent of which learned architecture it is.

## Connecting back to `runs/ablation/cpu_run1/ANALYSIS.md`: what these figures add that the tables alone do not

That document's headline findings (Transformer wins on point estimate but is the least *consistent* model at 168% relative variability; only "GBT beats RandomForest" and "Transformer beats RandomForest" survive a non-overlapping-CI standard; SSL pretraining is now a clean negative on the chained metric for both architectures) are all numeric, derived from the `per_seed` final-error arrays alone. This folder's figures supply the visual evidence those numbers describe but do not show:

- `train_transformer.png`'s visibly fanning-out seed curves are the training-time origin of the CoV finding, not just its numeric consequence -- the instability is present from early epochs, not only in the final chained-error snapshot.
- `comparison_val_loss.png` next to `ablation_matrix.png` is the first time in the project the windowed-vs-chained comparison has been run on the *same* set of six models at *matched* settings (batch=64, 3 seeds each) rather than across separate single runs at different configurations -- and it surfaces a genuine ranking reversal (SSL-Transformer marginally ahead on windowed loss, clearly behind on chained error), the cleanest instance of that recurring caution yet documented in this project.
- `trajectory_xy.png` and `trajectory_xz.png` together show *where* the six models' accuracy differences actually live (horizontal drift, not altitude), a decomposition the single scalar final-error number in the results table cannot express on its own.
- `error_over_time.png`'s shared error-ramp structure across all six architectures is a new observation not present in `runs/ablation/cpu_run1/ANALYSIS.md` at all -- consistent with, and a further concrete instance of, that document's standing data-sufficiency diagnosis (a single continuous flight, not diverse sessions) affecting every model similarly rather than any one architecture uniquely.

## What remains a limitation, stated plainly

- RandomForest and GBT have no training-curve figures in this folder, and none should be expected -- both are single-shot `GridSearchCV` fits per seed, not epoch-trained models, so there is no per-epoch quantity to plot. `comparison_val_loss.png`'s single bar per model, using each seed's one `val_mse` value, is the correct and complete substitute, not an approximation of a missing curve.
- The representative-seed trajectory figures (3D/XY/XZ/error-over-time) each show one seed's path per model, chosen by the documented median rule; they are not a substitute for `runs/ablation/cpu_run1/ANALYSIS.md`'s CI-based statistical claims, and should not be read as "the" trajectory for the Transformer or any other model, particularly given how wide that model's own seed-to-seed spread is. A reader who wants the statistically defensible claim should look at the CI table, not at which single line is greenest in `trajectory_xy.png`.
- As in `runs/ablation/cpu_run1/ANALYSIS.md`, every finding here is drawn from n=3 seeds -- real evidence that variance exists and roughly how large it is, not enough to pin down a precise mean for the more variable models (Transformer, SSL-Transformer) with high confidence.
