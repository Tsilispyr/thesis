## 3. Reframing: What "Connectivity Prediction" Means Here

Clarified directly with the thesis author: **Connectivity Prediction is not about forecasting *when* a signal will drop.** It is about, *given that GPS/connectivity has already dropped*, reconstructing the drone's position/path from onboard, connectivity-independent data collected during the current flight - motor/actuator command logs, barometer (altitude), magnetometer/compass (heading), and IMU - so the drone can be routed home. This is a sensor-fusion extension of the existing dead-reckoning LSTM, not a new failure-time-prediction model. Path Recovery is the downstream behavior that consumes this reconstructed position to plan and execute a return.

The Self-Supervised Learning angle: the current Δposition regression (labels auto-derived from trajectory, no manual annotation) is an acceptable base, but a genuine SSL pretext task - pretraining on the large unlabeled IMU corpus via masked-sequence reconstruction or contrastive predictive coding, then fine-tuning for the regression target - should be attempted, evaluated as an ablation against the from-scratch baseline, and kept if it measurably improves results or generalization.

Timeline: more than a month is available. Engineering on all tracks happens first; a rigorous, thesis-grade analysis and write-up phase follows once the tracks are functional.

## 7. Second Critical Finding: Domain-Shift Scaler Contamination (Run D)

The pipeline was rerun with the leakage fix. Honest results:

| Run | Sources | Norm | Val Loss | Note |
|-----|---------|------|----------|------|
| A | nav only | No | 11148.4 | unusable, as before |
| B | nav only | Yes | 0.9622 | data-starved, as before |
| C | imu only | Yes | **0.7466** | cross-validated independently by `train.py`'s ~0.72–0.81 - trustworthy |
| D | nav + imu | Yes | **0.0669** | implausibly good - investigated below, **not trustworthy** |

Run D's number is a red flag for the same reason the leaked numbers were: train loss (1.03) is *higher* than val loss (0.067), an 11x gap in the wrong direction. Root-caused via direct inspection of the raw CSVs:

- nav's last row: `latitude≈37.777°, longitude≈-122.425°, altitude≈163m` (real GPS coordinates)
- imu's first row (after `pos_x/y/z → latitude/longitude/altitude` renaming): `0.0, 0.0, 15.0` (relative metres)

`step9_run_D()` does `pd.concat([nav, imu], ignore_index=True)`, then `_build_sequences()` computes `.diff()` on the concatenated `latitude`/`longitude`/`altitude` columns to build the delta targets. At the single row where nav ends and imu begins, this produces a delta of roughly **(-37.8, +122.4, -148)** - a target-space outlier about 1000x larger than a normal per-step delta (~0.01–0.05). `StandardScaler.fit()` over the full target array is dominated by that one outlier's squared deviation, inflating the fitted standard deviation several-fold. Since MSE loss is computed in *normalized* space, the inflated denominator shrinks the apparent error for all ~549,516 unaffected rows. The model didn't get better - the measuring stick got longer.

This is the same "domain-shift bug" already named in the original audit (nav = GPS degrees, imu = relative metres), but the *old*, leakage-corrupted numbers showed it making Run D look *worse* (0.3325 vs. Run C's 0.2264). The same root cause, once the unrelated leakage bug is fixed, instead makes it look artificially *better* - arguably more dangerous for a thesis, since it reads as a positive result worth reporting.

**No number involving combined nav+imu training - past or present - should be cited until nav's coordinates are unified into imu's relative-metre frame (Haversine/ENU projection) before concatenation. Until then, Run C (0.7466) is the only trustworthy baseline in the project.**

## 10. Fourth Finding: `uav_navigation_dataset.csv` Is Not a Real Trajectory

Item 1 of the revised Phase 2 plan (§9) was implemented: `dataset_parser.py` now computes `delta_lat/lon/alt` per-source (nav converted from GPS degrees to metres via an equirectangular projection, imu unchanged), tags rows with `_src_id` so `create_dead_reckoning_dataset()` skips any window that would straddle the nav/imu boundary, and fits `StandardScaler` on the train split only. Verified in isolation: `python ai_backend/data_processing/dataset_parser.py` correctly produces 549,507 combined sequences (549,517 possible − 10 correctly dropped at the boundary, exactly matching `window_size=10`).

Rerunning the full pipeline with all three fixes, however, produced **Run D val loss = 0.0000** - worse than the previous artifact (0.0669), not fixed. Direct inspection of the raw CSV explains why:

```
   timestamp             latitude    longitude     altitude   speed
0  2023-01-01 00:00:00   37.772391  -122.421527   218.14      26.18
1  2023-01-01 00:00:01   37.783914  -122.419931   199.81      17.36
2  2023-01-01 00:00:02   37.779540  -122.412309   129.27       9.89
```

Consecutive rows are exactly 1 second apart, but the lat/lon jump between them implies **~1,000–2,200 metres of movement per second** - while the same rows' own `speed` column says 7–30 m/s (i.e., ≤30 m of real displacement possible). These two things cannot both be true. Checked across the full file (`delta_lat` in metres: std ≈ 909, max ≈ 2,202 - even *before* any obstacle-row filtering or boundary effects): **`uav_navigation_dataset.csv`'s position columns are not a continuous flight recording.** They read as independently-randomized values per row, arranged behind sequential timestamps to look like telemetry. No unit conversion can fix this, because the underlying data has no real spatial continuity for `.diff()` to extract - this isn't the "domain-shift" (degrees-vs-metres) problem originally diagnosed in the audit, it's a data-generation problem one level deeper.

**This retroactively explains a pattern present in every session's docs going back to the original `STATUS.md`**: Run B (nav-only) has always plateaued at val loss ≈ 1.0 ("predict the mean") and been labeled "data-starved" - but data volume was never the issue. The delta-position target derived from this file is close to random noise with respect to the IMU input features, so there was never a learnable relationship for more data or more epochs to surface.

**Consequence:** `uav_navigation_dataset.csv` should not be used to derive dead-reckoning position-delta targets - not now, not after any unit fix. Practical path forward:
- Treat **Run C (imu-only) as the sole trustworthy dead-reckoning baseline**, full stop - not "trustworthy pending a nav fix," but the actual intended production data source going forward.
- Retire Run B and Run D from the pipeline's "current results" framing (they can stay in the code as a documented historical/negative-result footnote - "we tried combining a second data source and found it was synthetic/unusable" is itself a legitimate thing to report in a thesis methodology section - but they should not appear as competing candidates for "best model").
- The nav CSV's *other* columns (`lidar_distance`, `wind_speed`, `battery_level`, `obstacle_detected`) may still be fine for whatever they were originally intended for (e.g., `path_recovery.py`'s rule-based signal-zone logic) - this finding is specifically about its `latitude`/`longitude`/`altitude` columns being unusable as a delta-position training target, not a claim that the whole file is worthless.
- The Haversine/ENU conversion work already done is not wasted: it's exactly the technique needed once a **real** second GPS-degree trajectory source exists - which is precisely what the Phase 1 flight-recorder (`--record` on `udp_server.py`) is for, now that `drone_body.gd` emits physically real telemetry. A recorded flight would have genuinely continuous `lat`/`lon` (from `drone_state.gps_lat/gps_lon` + real position deltas), unlike this file.

**Resolved (2026-07-23):** the user asked to dig in further - treating this as a genuine problem, not something to rationalize - and to search for free, real replacement data. Findings and actions below (§11).

## 14. `breadcrumb_recovery.gd` - Implemented (Goal 3, Emergency Floor)

New file: `simulation/scripts/breadcrumb_recovery.gd` - a plain `RefCounted` class (`class_name BreadcrumbRecovery`, deliberately not a `Node`, so it has no scene-tree dependency and is directly unit-testable in isolation). Implements exactly the spec from §12 Goal 3:

- **Buffer**: `record_sample(v_world, dt)` accumulates world-frame velocity samples, storing one decimated entry every `DECIMATION_INTERVAL` (2 Hz / 0.5s) into a capped `Array` (`MAX_BUFFER_SAMPLES = 240`, i.e. 2 minutes of history). In-sim, `v_world` is `RigidBody3D.linear_velocity` directly (already world-frame); the class docstring notes this is mathematically what `R(q)·v_body` reconstructs on real hardware, where only body-frame IMU-derived velocity is available.
- **Health tracking**: `mark_healthy()` resets a `Time.get_ticks_msec()`-based timer. `should_trigger()` returns true once `TRIGGER_TIMEOUT_MS` (500) has elapsed with no `mark_healthy()` call *and* the buffer isn't empty - this is the real, computed health signal, not a placeholder.
- **Recovery**: `pop_next_reversal_command()` pops the buffer from the back, returning the **negated** stored velocity - pure command-replay, no controller loop. Returns `null` once exhausted.

**Wired into `drone_body.gd`**:
- `_breadcrumb := BreadcrumbRecoveryScript.new()` where `BreadcrumbRecoveryScript := preload("res://scripts/breadcrumb_recovery.gd")` - preloaded rather than referenced by bare `class_name`, so it works correctly even before Godot's global script-class cache has been refreshed by opening the project in-editor.
- In `_physics_process()`: while `gps_signal` is true, calls `_breadcrumb.mark_healthy()` + `_breadcrumb.reset()` every frame (only the *current* loss episode's history is kept) and always calls `record_sample()`. Once `gps_signal` is false and `_breadcrumb.should_trigger()` fires, control branches into a new `_run_breadcrumb_recovery()` function instead of the normal `_update_stabilisation()`/`_mix_motors()`/`_apply_forces()` path - direct `linear_velocity` override, replaying buffered commands at their original decimated intervals. When the buffer drains, `should_trigger()` naturally goes false again and control falls straight back through to normal stabilisation/hover on its own (no explicit "recovery complete" state machine needed - the drone should be back near its origin by then, and normal auto-hover takes over).
- `apply_ai_correction()` (called by `udp_bridge.gd` whenever a fresh AI correction arrives) now calls `_breadcrumb.mark_healthy()` first - proof a higher layer of the hierarchy (RL/SSL-LSTM/EKF, whichever produced the correction) is alive, standing the emergency floor back down.

**Deliberate simplification, noted not hidden**: during replay, only `linear_velocity` is overridden - no attitude/orientation correction is applied, matching the spec's "pure command-replay, no controller loop" requirement exactly. The drone may look visually tilted during retrace since nothing actively levels it. Acceptable for a last-resort, zero-AI behavior; flagged as a possible follow-up (a minimal auto-level torque) rather than a blocking gap.

## 15. SSL Masked-Reconstruction Pretext Task - Implemented and Smoke-Tested (Goal 1 item 2)

## 16. Classical EKF Baseline - Implemented and Verified (Goal 1 item 4 / Goal 3 tertiary layer)

New file: `ai_backend/models/ekf_baseline.py`. A real, reusable estimator (not a strawman comparison script), serving two roles: the non-ML floor of Goal 2's 5-model ablation matrix, and the tertiary layer of Goal 3's fail-safe hierarchy.

- **`DeadReckoningEKF`**: 6-dimensional state `[px, py, pz, vx, vy, vz]` (world frame). `predict(accel_body, rotation_matrix, dt)` propagates via strapdown double-integration - the exact same specific-force convention already established for the simulated accelerometer (§6.1, eq. 1), run forward instead of backward - with a standard discretized piecewise-white-noise-acceleration process-noise model (the textbook Kalman-filter INS derivation, not an invented shortcut). `update_baro(altitude)` performs a standard linear measurement update correcting `pz` (and, through the cross-covariance terms, `vz`).
- **Not an invented fusion pattern**: barometric altitude correction is exactly what PX4's own EKF2 does - confirmed directly by having inspected `vehicle_local_position.z` in the real PX4 logs downloaded for this project (§11.2), rather than assumed from a textbook alone.
- **Uncertainty for free**: `position_covariance` / `position_uncertainty` properties expose the propagated covariance directly - this is Goal 1 item 5's uncertainty requirement, native to a Kalman filter (unlike the LSTM/Transformer, which need an explicit Gaussian-NLL output head to get the same thing).
- `rotation_from_euler_deg()`: standalone helper building the world-from-body rotation matrix from roll/pitch/yaw in degrees, matching the exact convention already used throughout `FEATURE_COLS`/`drone_body.gd`.

**Verified with a synthetic smoke test** (`python ai_backend/models/ekf_baseline.py`) that demonstrates the actual reason to prefer an EKF over pure inertial integration - exactly the narrative Goal 4 Category B's drift-comparison figure is built around: a stationary drone integrated for 5s (10Hz, noisy accel) drifts to **1-sigma position uncertainty of 5.20m on every axis** under pure inertial integration alone; with a periodic (2Hz) noisy barometer correction, the vertical-axis uncertainty drops to **0.26m** (final altitude estimate 9.95m vs. 10.0m true) while the uncorrected horizontal axes remain at 5.20m, exactly as expected - the correction only constrains the axis it measures. Asserted in code, not just eyeballed: `ekf_with_baro.position_uncertainty[2] < ekf_no_baro.position_uncertainty[2]`.

**Not yet done**: integration into Goal 2's actual benchmark run (evaluating the EKF over real windowed flight data and computing position error vs. ground truth in the same terms as the LSTM's reported val loss) - that requires a small adapter between this class's continuous state-propagation API and the windowed-sequence evaluation harness the LSTM models use, which is Goal 2's job, not this item's. **Partially superseded by §17 below** - a continuous real-trajectory evaluation now exists (arguably more useful than a windowed-MSE-equivalent), just not yet folded into a full multi-seed Goal 2 matrix.

### 18.2 `recovery_orchestrator.py`: making the live hierarchy Python-testable, not Godot-only

The live correction path before this point was LSTM-only (`udp_server.py::_predict_correction`, no EKF, no rule-based fallback) - the "degrade toward simplicity" hierarchy existed as a design and as isolated, independently-verified pieces (§13-§16), not as one live, switching system. Per an explicit user request - given this environment can't run or watch the Godot GUI, keep the new orchestration logic in Python where it's headlessly testable - all of it was factored into a new, dependency-free class: `ai_backend/api/recovery_orchestrator.py::RecoveryOrchestrator`. `udp_server.py` was thinned to a dozen lines that just call `orchestrator.decide()` and forward the result.

`decide()` picks LSTM once its 10-step buffer is warm, else steps a per-drone `DeadReckoningEKF` (§16) using the telemetry's `baro_alt`, else falls back to a rule-based vector - the same three layers Goal 2's benchmark matrix already names, now live. A `python ai_backend/api/recovery_orchestrator.py` smoke test (no sockets, no Godot) exercises all three transitions plus a staleness-reconnect guard. That guard's own test caught a real bug during development: resetting a drone's EKF/buffer state after a multi-second reconnect gap still fed the *raw* gap forward as `dt`, so the freshly-reset EKF's first `predict()` integrated across the whole gap and produced a ~49 m/s spike - exactly the corrupted-dt failure mode the guard was built to prevent, just relocated one line later. Fixed by clamping `dt` to a fresh-first-packet default (0.1s) specifically on the stale-reset path, and the smoke test now asserts an upper bound on the resulting velocity magnitude, not just "no crash," so this class of bug can't silently regress.

### 18.3 `live_mission_demo.py`: a second, fully self-verifiable front end

Because the Godot side is only verifiable by a human, a second, standalone front end was built: `ai_backend/live_mission_demo.py`, a simple point-mass drone simulated directly in Python (physically-consistent specific-force/attitude derivation, same conventions as `drone_body.gd`, same `RecoveryOrchestrator`), rendered as a live matplotlib 3D plot styled identically to the offline thesis figures (`plot_style.py`'s cyan/magenta/black roles), with a scrolling decision log and on-figure mission controls. Its `--headless-test` mode scripts a full mission/cut/recover/restore sequence with no display and saves a PNG snapshot - this is what let real layout bugs (a title overlapping the axes title, a clipped "RESTORE GPS" button, both from the widget-region math) get caught and fixed from a saved image, the same verification loop used for every offline figure this session, rather than needing a human to run it first.

### 18.4 The flat-correction finding, and why the fix is a legitimate addition, not a fudge

Testing the Python tool surfaced a real, informative property: once GPS is cut, LSTM's correction converges within ~1-2s to a small, nearly-constant value and stays there - the drone just coasts. Root cause: LSTM/EKF are pure dead-reckoning *estimators* ("what am I probably doing right now"), not target-seeking controllers ("how do I get back on course") - with the mission autopilot correctly suspended and nothing else driving acceleration, the IMU window becomes near-static and the per-window estimate (correctly) converges to near-zero. This is consistent with, not contradicted by, the offline finding that this model predicts small per-window deltas (§17.3's normalized-loss numbers were never large to begin with).

Presented to the user as a design decision, not silently patched: keep it as an honest pure-estimator (matches the offline evaluation exactly), or add real target-seeking. Chosen: add it. `RecoveryOrchestrator` now maintains a per-drone running position *belief* (`believed_pos` - anchored at the last known-good position, integrated forward each tick by whatever velocity was just commanded) and blends a small, distance-proportional, capped pull (`SEEK_KP=0.15`, `SEEK_MAX_CONTRIB=1.5 m/s`) toward the current goal on top of the raw LSTM/EKF estimate. This is legitimate, not a fudge, for the same reason real return-to-home systems do it: the destination coordinate is a stored waypoint, known independent of the live GPS fix that's actually missing - only the *current* position is uncertain. Rule-based's existing target-vector logic was also switched from the frozen loss-instant anchor to the same evolving `believed_pos`, so a long recovery episode doesn't keep steering from a stale starting point.

### 18.5 "Does it RTL, or go to target then RTL too?" - the target-then-RTL hybrid

A direct, good question from the user about the seek-bias addition: does the drone RTL, or keep pushing for the original target forever? Honest answer at the time: neither, really - it pulled toward whatever `mission_target` was set, indefinitely, with no notion of "home" anywhere in the system; the only RTL-*like* behavior was breadcrumb's path-reversal, which retraces the flown path rather than flying a direct line to a stored launch point.

Presented as a real three-way design choice (target-only / RTL-immediately / hybrid) rather than assumed - the user chose the hybrid. Implemented entirely in `RecoveryOrchestrator`, so it's automatically live in both front ends with no duplicated logic: a `home_pos` is latched from the very first telemetry packet ever seen for a drone (regardless of GPS state - home is a stored waypoint, the same way a real autopilot latches home at arm time, not something re-derived from a live fix). The goal seeking `mission_target` switches to `home_pos` - sticky for the rest of that loss episode - once `RTL_TIMEOUT_S` (8s) of continuous GPS loss elapses *and* the estimated distance to target is still above `RTL_SKIP_IF_CLOSE_M` (3m, so a near-arrival isn't pointlessly aborted). No mission target at all means home is the only sensible goal from the start. The result is reported back as a new `"goal": "TARGET"|"HOME"|"NONE"` field alongside `"layer"`, threaded through `udp_server.py`'s wire payload, `drone_body.gd::apply_ai_correction()` (which logs a one-time `"RTL ENGAGED"` line on the transition, mirroring breadcrumb's own one-shot trigger log), and `live_mission_demo.py`.

Verification here is where the smoke test earned its keep a second time: a naive test that jumped `now` forward by ~8s in one call looked to the orchestrator exactly like a stale reconnect (`STALE_GAP_S=2.0`), not 8 seconds of continuous connection - it reset the episode instead of exercising the timeout. Fixed the *test* (step through in realistic 0.1s increments, matching real telemetry cadence, measuring elapsed time from when the loss actually started rather than from the test's absolute clock zero) rather than the orchestrator, since the orchestrator's behavior was correct and the test's shortcut wasn't representative. A second, genuine bug was caught in the same pass: the routine per-tick correction log line was firing every 0.1s, and over a ~30s continuous-loss window that flooded the capped 200-line log buffer and evicted the one-shot `"RTL ENGAGED"` line before the headless test's own assertion could see it - fixed by throttling the routine log to ~1/s, which also directly improves the interactive tool's actual usability (a real user would have hit the same problem).

`live_mission_demo.py --headless-test` now runs a scenario specifically shaped to force the hybrid's RTL branch (target cut early, far enough that the capped seek can't close the gap within 8s) and asserts `"RTL ENGAGED"` appears in the log - end to end, the saved snapshot shows the correction sign visibly flipping at the engagement point (`v=(1.06, 0.16, 0.95)` toward the target, then `v=(-1.12,-0.19,-1.00)` toward home immediately after) and the predicted-path line curving back on itself in the plot.

### 18.6 A second, real finding from interactive use: layer responsiveness is asymmetric by design

Manually switching the HUD's Force Layer control between LSTM/EKF/RULE_BASED near an already-close target, the user observed RULE_BASED as consistently fastest/most decisive, EKF middling, LSTM slowest, and Auto (which resolves to LSTM once warmed up) looking "stuck" once close. Confirmed as a real, explainable asymmetry rather than a bug: `_rule_based_velocity()` always commands the full fixed `RULE_BASED_SPEED_MPS` (2.0 m/s) with no distance-based decay at all, while `_apply_seek_bias()` (feeding LSTM/EKF) is deliberately distance-proportional and capped - it's *supposed* to shrink toward zero near the goal. Rule-based's lack of an arrival taper means it would in principle oscillate/overshoot rather than settle, which is a legitimate, documented characteristic of that layer (a deliberately "dumb but decisive" fallback) - noted here rather than silently harmonized, since changing it wasn't requested and the asymmetry is informative for the thesis write-up (each layer has a genuinely different closed-loop character, not just a different position-estimation method).

`AI_Recovery/screenshots/live_mission_demo.png` (regenerable via `live_mission_demo.py --headless-test --out screenshots/live_mission_demo.png`) captures the full target-then-RTL arc described in §18.5 and is now embedded in `ai_backend/README.md` and the top-level `AI_Recovery/README.md` (§5). `simulation/README.md`, `simulation/CODEBASE_DOCS.md`, `simulation/scripts/README.md`, `ai_backend/README.md`, `ai_backend/api/README.md`, and `ai_backend/models/README.md` were all updated for the new files (`recovery_orchestrator.py`, `live_mission_demo.py`, `mission_log.gd`, `trajectory_visualizer.gd`), the new wire-format field (`"goal"`), the corrected camera target, and the retired 15-second auto-timer. `STATUS.md` and `EXECUTION_GUIDE.md`, both long stale relative even to §1-§17 (last touched session 5, before the nav-dataset investigation), were brought current in the same pass rather than left further behind.

**Where this came from**: the user asked to mine their own MSc coursework (`D:\ΠΜΣ\`, ten course-project folders spanning PyTorch, R, Scala/Spark, Java/Hadoop, KNIME) for proven, reusable techniques and apply as many as genuinely fit to this project, both to progress the roadmap with real rigor and to broaden the thesis's technical surface. Verdict at the time: enough to proceed, but flagged as a real risk specifically for the Transformer arm (no recurrent inductive bias, typically wants sequence *diversity* more than raw row count) and for seed-to-seed variance generally -- both risks materialized exactly as anticipated, see §19.4 and §19.7-§19.8.

### 19.1 A1 -- Gyro Unit Reconciliation (imu/px4): an honest non-fix

`ai_backend/data_processing/reconcile_gyro_units.py` swept every plausible unit-conversion candidate (rad/s↔deg/s, common gyro full-scale sensitivities 250/500/1000/2000 dps) against both sources' actual standard deviation, reusing `dataset_parser.py::verify_unit_consistency()`'s own std-ratio metric. **No candidate reconciled the two sources** -- the mismatch is not a units bug, it is a genuine dynamics difference between the simulated `imu` flight and the real PX4 hardware logs (`datasets/px4_raw/GYRO_UNIT_ANALYSIS.md` has the full sweep table). §4's pending item ("reconcile the imu/px4 gyro mismatch") is now answered, just not in the direction hoped: the ablation matrix proceeds on `imu` alone, as it always would have without a fix, and `px4` stays held out for chained-trajectory evaluation only. This is the same honest-negative-result pattern as the SSL finding in §17.2 -- investigated properly, reported as-is, not forced.

### 19.2 A2 -- Uncertainty Head (Gaussian NLL)

`ai_backend/models/dead_reckoning_model_uncertainty.py::DeadReckoningLSTMUncertainty` -- the same LSTM backbone, regression head widened to output mean + log-variance (clamped `[-10,10]`), trained with `gaussian_nll_loss()` (Kendall & Gal 2017). A new class, not a modification of `DeadReckoningLSTM` -- the live orchestrator loads the production model by exact class shape, and this arm is additive/offline-only, same discipline as every other Track A phase.

**A real, non-obvious training-dynamics finding**: validation NLL's best epoch (1) and validation MSE-on-the-mean's best epoch (6) disagree -- MSE keeps improving for several epochs after NLL says stop, because the model's variance head shrinks faster than its accuracy improvement warrants (increasingly overconfident, which NLL correctly penalizes and plain MSE cannot see). Restoring epoch-1 weights is the right call for a calibration-focused model, but it does mean this arm trades some chained accuracy for calibration (29.44m vs. the plain LSTM's 26.34m at the time).

**Calibration, checked directly, not assumed**: `evaluate_trajectory.py::uncertainty_calibration()` correlates predicted uncertainty magnitude against actual chained error on the same held-out segment. Result: **r = 0.203**, weakly positive -- real signal, far from a usable confidence measure. The EKF's native covariance, checked the same way on the same segment, scores r = 0.999 -- not evidence the EKF is "better at uncertainty" in any deep sense, its covariance is a near-deterministic function of a fixed process model and correction schedule, while the LSTM head has to infer confidence from data content alone, a genuinely harder, data-diversity-limited problem. Retrained three times over the course of this session (once originally, once at batch=256/GPU, once restored to batch=64): chained error 29.44m / 31.69m / 38.54m, calibration r 0.203 / 0.212 / 0.119 -- this arm's number is real but noticeably less reproducible run-to-run than the plain LSTM's, itself a preview of the seed-variance theme that dominates §19.7-§19.8.

### 19.3 A3 -- Transformer Dead-Reckoning Arm (+ SSL variant): the phase that ended up mattering most

`ai_backend/models/dr_transformer.py::DeadReckoningTransformer` -- `d_model=64` (matched to the LSTM's `hidden_size=64` for a fair comparison), `nhead=4`, 4 encoder layers, pre-norm, hyperparameters taken directly from the confirmed-working `TinyViT` reference in the user's own Computer Vision coursework. A 10-timestep IMU window has no 2-D patch structure, so `PatchEmbed`'s `Conv2d` is replaced by a per-timestep `Linear` projection -- the direct temporal analogue. A hand-written encoder layer (not stock `nn.TransformerEncoderLayer`) so attention weights are retrievable for interpretability without depending on private internals. Given the data-sufficiency risk flagged above, dropout (0.1) and `augment_batch()` (jitter/scale/time-warp, the time-series analogue of the CV coursework's image augmentations) are baked in from the start, not added reactively.

**Real result, at the originally-validated batch=64**: windowed val loss 0.3545 (roughly half the LSTM's), and -- the check that matters -- chained-trajectory error **12.46m final / 9.75m mean**, beating the LSTM's 26.34m outright, on the same held-out segment. Attention weights, extracted over 500 real windows: **only layer 0 shows real temporal selectivity** (U-shaped -- highest at the window's oldest and newest steps, lowest mid-window); layers 1-3 are statistically indistinguishable from uniform. A genuinely non-obvious, honestly-reported limitation: the Transformer's real advantage over the LSTM does not appear to come from deep multi-layer attention reasoning.

**SSL variant** (`ssl_pretext_transformer.py`, mirroring `ssl_pretext.py`'s two-stage structure exactly): another honest negative, consistent with the LSTM's own SSL finding in §17.2 -- pretraining converges cleanly (no overfitting), but fine-tuning from it does not beat from-scratch (chained 17.91m vs. 12.46m at the time, though that specific run was later found to have been trained at a different batch size than the rest of the comparison -- see §19.6). SSL not transferring usefully now holds for both architectures, strengthening the case that the pretext task or the single-flight data's lack of diversity is the limiting factor, not something specific to either architecture.

### 19.4 A4 -- Classical-ML Baseline Bench + Anomaly-Detection Gate

`ai_backend/models/classical_baselines.py` -- `RandomForestRegressor` and `MultiOutputRegressor(HistGradientBoostingRegressor(...))` (the histogram-based GBM, chosen over plain `GradientBoostingRegressor` specifically because the latter's exact-split algorithm is impractical at this data's ~436K-row scale), `GridSearchCV`-tuned on a 20K-row subsample then refit on the full training set. Answers the project's own "deep learn / ML / RL" framing literally -- until this phase, the ablation matrix had classical-DSP (EKF) and deep learning (LSTM) but nothing representing plain supervised ML.

**A genuinely striking result**: GBT trains in ~48 seconds (versus the LSTM's ~170s or the Transformer's ~3300s) and reaches windowed val MSE 0.3546 -- competitive with the Transformer's 0.3545 at the time -- and chained error 18.06m, beating the LSTM outright despite having zero sequential modeling capability at all (it sees the window flattened to 140 columns, order discarded). RandomForest's windowed MSE (0.6665) looked competitive with the LSTM's but did **not** carry through to chained accuracy (27.24m, essentially tied with the LSTM) -- another concrete instance of the windowed-vs-chained gap this project keeps finding.

`ai_backend/models/anomaly_gate.py` -- `IsolationForestGate` and an independent `PCAReconstructionGate`, run side by side on the same flattened windows. A genuinely different signal from either uncertainty source above: these flag input pathology (sensor glitches, corrupted windows), not motion uncertainty.

### 19.5 Infrastructure: an AMD GPU detour, and a batch-size finding that shaped everything after it

Mid-Track-A, the user pointed out an AMD GPU was available and pointed at their own coursework's proven DirectML setup (`D:\ΠΜΣ\Βαθιά Μάθηση\...\25118.py`) as the pattern to reuse. `ai_backend/device_utils.py::get_device()` was built to match it, and a Python 3.10 standalone environment (the user's own, already carrying the exact pinned `torch==1.13.1`/`torch-directml` versions DirectML's older API needs) was used rather than touching the shared global environment other projects depend on.

**The real finding**: at `batch_size=64` (every model's default), a direct A/B test showed batch=256 trains faster and reaches better *windowed* validation loss on GPU -- but a direct chained-trajectory comparison, the metric this whole project has repeatedly established as the one that matters, showed batch=256 reaching **substantially worse real accuracy** (LSTM 37.18m vs. 26.34m; Transformer 29.60m vs. 18.33m at the time) despite its better windowed number -- a plausible large-batch-SGD sharper-minima effect, and the starkest instance yet in this project's history of "an isolated metric looking better is not evidence of real improvement." Resolution: every model kept `batch_size=64` as its default, the config with actual chained-accuracy evidence behind it. Two real, durable bugs were found and fixed along the way, independent of the batch-size question: a checkpoint-portability bug (DirectML-trained tensors need `.cpu()` before `torch.save()` or `torch.load()` rejects them elsewhere under `weights_only=True`, now fixed at the source in every training script) and a `random_mask()` performance bug (a per-sample Python loop measured at 156ms/call, vectorized to 0.9ms/call, 173x faster, verified to produce identical masking statistics).

**A second, later finding sharpened this further**: once the formal ablation matrix (§19.7) was actually run on real hardware, DirectML at batch=64 turned out to be roughly **9x slower per epoch than plain CPU** on this machine -- far worse than the ~1.2x the raw-throughput micro-benchmark alone suggested, because DirectML's per-operation dispatch overhead (it is a translation layer over DirectX12, not a first-class backend like CUDA) dominates at small batch sizes, compounded by the LSTM's recurrence turning even a batch of 64 into many small sequential dispatches. Since batch=64 is not changing, `get_device()` was changed so DirectML is now opt-in (`prefer_directml=True`) rather than the default -- CPU is the correct default for this project's fixed training regime, not a fallback.

### 19.6 A5 -- Formal Multi-Seed Ablation Matrix: two runs, `cpu_run1` and `cpu_5seeds`

`ai_backend/ablation_matrix.py` -- trains/evaluates all 6 stochastic arms (LSTM, SSL-LSTM, Transformer, SSL-Transformer, RandomForest, GBT) across multiple seeds plus both deterministic baselines (EKF, pure inertial), reporting mean ± t-distribution 95% CI (not a fixed z=1.96, correct at small n) on the same held-out chained-trajectory segment every other evaluation in this project uses. Two real infrastructure additions made this practical: every training script now persists a complete, uniquely-tagged checkpoint per seed (previously only the LSTM did; the other five arms either overwrote each seed's files or, for the SSL and classical arms, never saved anything to disk at all during an ablation run -- found and fixed while investigating whether per-epoch logs were being kept durably), and the script is fully resume-safe (`--seed-list`, cached-checkpoint detection) so an interrupted run never re-pays for seeds it already finished.

**`cpu_run1` (3 seeds, first complete run)** -- full results and figure-by-figure walkthrough in `runs/ablation/cpu_run1/ANALYSIS.md` and `runs/ablation/cpu_run1/figures/ANALYSIS.md`. Headline: Transformer wins on point estimate (8.18m final) but is also, by a wide margin, the *least consistent* model in the matrix (three seeds spanning 3.22-14.17m, a coefficient of variation of 168% -- larger than its own mean); RandomForest is the most consistent (5%). At only 3 seeds, the only statistically clean (non-overlapping-CI) pairwise wins were "GBT/Transformer beat RandomForest" -- "Transformer beats LSTM" was not yet provable (a 1.27m CI gap, effectively a coin flip).

The extra seeds bought a materially stronger claim: **Transformer now cleanly beats 4 of the other 5 arms** (LSTM, SSL-LSTM, RandomForest, and now GBT too -- the GBT comparison was the one that flipped), only remaining statistically tied with its own SSL-pretrained variant. This also *revised* part of the §19.3 interpretation: since GBT (order-blind) is no longer tied with the Transformer, "the Transformer's edge is just nonlinear feature combination, not sequence reasoning" is a weaker claim than it looked at 3 seeds. The reliability finding held up directionally (Transformer still the least consistent, 71% CV; RandomForest still the most, 2%) even as every CI tightened. A genuinely new finding only visible at 5 seeds: the LSTM's own training curves split into two groups -- three seeds early-stopped within 6-10 epochs, one seed (3) ran to epoch 10, and one seed (4) **never triggered early stopping at all**, still improving at epoch 30, and independently had both the best windowed loss and the best chained error of all 5 -- see §19.8.

### 19.10 Testing five of §19.9's own open questions directly, using only artifacts already on disk

Five of the concrete follow-ups §19.6-§19.9 named were tested directly rather than left as unexamined proposals -- none required new flight data or Godot access, all reused the exact evaluation methodology (chained-trajectory error on the same held-out segment) every other number in this report uses.

**Does ensembling the Transformer's 5 already-trained seeds mitigate its reliability problem?** `ai_backend/evaluate_transformer_ensemble.py` averages all 5 `cpu_5seeds` checkpoints' per-step delta prediction at each chained-trajectory step (before chaining, not a post-hoc average of 5 independently-drifted trajectories), reusing `evaluate_trajectory.py`'s own chaining/scaling conventions exactly. Result: **3.92 m final / 5.88 m mean**, against a per-seed final-error range of [3.22, 15.04] m and the ablation study's own reported expected value of a random single seed (`final_mean` in `results.json`, 9.10 m). Ensembling does not beat the single luckiest seed (3.22 m), it cannot, no method can know in advance which untrained seed will be lucky, but it lands close to that best case and roughly halves the error a randomly-deployed single seed would be expected to produce, for free, from checkpoints that already existed. A genuinely actionable, no-retraining mitigation for the reliability problem, not a fix for the underlying cause.

**Does separating mu/log_var training fix the uncertainty head's weak calibration?** `ai_backend/train_uncertainty_two_phase.py` implements `ai_backend/models/ANALYSIS.md`'s own proposed fix: phase 1 trains the full model on plain MSE(mu, target) to convergence (early-stopped on val MSE, independent of any NLL/variance dynamics); phase 2 freezes the shared trunk and mu's own output rows, training only the log_var rows of the shared final `nn.Linear` layer on `gaussian_nll_loss`. Freezing mu at the parameter level isn't possible with a plain `requires_grad=False` here (mu and log_var share one linear layer, split by row, not two separate heads), so phase 2 zero-masks the mu rows' gradient every step before the optimizer applies it. **A real bug was found and fixed while building this**: the first run showed mu's val MSE drift from 0.7080 (end of phase 1) to 1.0314 (one epoch into phase 2) despite the masking, traced to Adam's `weight_decay` re-adding a nonzero `weight_decay * param` term to the already-zeroed gradient inside its own `step()` internals, undoing the mask; fixed by setting `weight_decay=0` on phase 2's optimizer (phase 2 only shapes 3 output rows, not the whole model, so the regularization pressure isn't needed there). Rerun confirmed the freeze held exactly (mu's val MSE identical, 0.7141, across every phase-2 epoch). **Result: an honest negative, mirroring the same pattern as the SSL and gyro-reconciliation findings.** Calibration barely moved (r=0.199 vs. the original's 0.203, well within the 0.119-0.212 range already observed across 3 retrains of the original single-phase model) and chained error came out worse (38.49 m vs. 29.44 m, though still inside that same model's already-documented 29-39 m run-to-run range). The binned calibration table looks more cleanly monotonic than the original's noisy middle bins, but the predicted-std range across all 5 bins is extremely narrow (0.03-0.07 in scaled units) -- freeing log_var to run for 9 dedicated epochs on pure NLL let it collapse toward a uniformly small, still-overconfident value rather than learning to genuinely vary with input content, the same overconfidence-race dynamic the original finding described, just relocated from epoch 1 into phase 2 instead of being cut short by it.

**Does the Transformer's real advantage over GBT depend on genuine chronological order?** `train_transformer.py` gained a `--shuffle-order` flag: a single fixed permutation of the 10 timestep slots (seeded, not per-window-random, so the model can still learn a consistent slot-to-content mapping, only chronological adjacency is destroyed), applied identically to every training and validation window. Trained fresh with otherwise-identical hyperparameters/augmentation. Windowed val loss came out close to the real Transformer's (0.3622 vs. 0.3545). The chained-trajectory result, evaluated with the same fixed permutation applied to the held-out segment (`ai_backend/evaluate_transformer_shuffled.py`): **9.78 m final / 7.24 m mean**, nominally *better* than the real, order-preserving Transformer's 12.46 m / 9.75 m, and still clearly ahead of GBT's 18.06 m. Taken at face value this is suggestive evidence against chronological order being the primary driver, consistent with the attention-interpretability finding (§19.3, only layer 0 shows real positional selectivity). **The honest caveat, stated plainly rather than glossed over**: this is one shuffled run compared against one order-preserving run, and the Transformer's own seed-to-seed variance is large enough (the same 5 ablation seeds span 3.22-15.04 m final error from random initialization alone, nothing to do with shuffling) that a single run landing at 9.78 m is fully consistent with ordinary seed noise, not necessarily evidence that shuffling is harmless. A real answer would need the same multi-seed treatment already applied to every other arm in this study (several shuffled seeds, compared by confidence interval, not point estimate) -- not yet run, and named here as the honest next step rather than overclaimed from n=1.

**That confirmation was then actually run, and the caveat turned out to be exactly right.** `ai_backend/train_transformer_multiseed_confirmation.py` trained the same 5 seeds (0-4) with `--shuffle-order`, `set_global_seed(seed)` called identically. Per-seed final error: 8.28 / 7.36 / 4.94 / 20.67 / 8.80 m (seed 3 a clear outlier) -- **mean 10.01 m, 95% CI [2.39, 17.64] m**, against the real order-preserving Transformer's 9.10 m mean, CI [2.61, 15.60] m. The two intervals overlap almost completely: **shuffling the input order is statistically indistinguishable from normal order**, neither clearly better nor clearly worse. The single-run "9.78 m, nominally better" result was exactly the ordinary seed noise the caveat anticipated it might be, not a real effect. Reported here as-is rather than left standing on the more exciting single-run number.

**Does raising the LSTM's early-stopping patience close the gap seed 4 revealed?** `ai_backend/train_lstm_patience_experiment.py` retrained the same 5 `cpu_5seeds` seeds with `patience=10` instead of 5, calling `ablation_matrix.py::set_global_seed(seed)` identically so each seed's initial weights match. Result, aggregated across the 5 seeds: final error **32.24 m mean** (39.43 / 26.69 / 36.66 / 31.36 / 27.04 m), *worse* than the original patience=5 run's 29.67 m mean -- no clean win. Seed-by-seed the picture is genuinely mixed: seed 1 improved substantially (29.48 m -> 26.69 m, best epoch 1 -> 25, real evidence patience helped that seed), two seeds got worse despite reaching similar or better windowed loss (another instance of the windowed-vs-chained gap this project keeps finding), and two were essentially unchanged.

**A more important, unplanned finding surfaced while investigating seed 4 specifically**: seed 4's rerun (patience=10) stopped at epoch 3 (val 0.7200), nothing like its own famous original behavior (never early-stopped, improved smoothly to epoch 30, val 0.6846) -- and since patience cannot affect what happens *during* epochs 1-3 (it only governs the stop decision), this divergence cannot be explained by the patience change itself. Two explanations were distinguished directly rather than assumed: (a) leftover state from training 4 other seeds first in the same Python process, or (b) a genuine cross-session reproducibility gap. Rerunning seed 4 alone, in a fresh process, with nothing else executed first (`ai_backend/train_lstm_seed4_patience10_isolated.py`), reproduced the sequential run's numbers *exactly* (epoch 1/2/3 val losses bit-for-bit identical), ruling out (a) cleanly. The remaining explanation is (b): `set_global_seed()`'s `random.seed()`/`np.random.seed()`/`torch.manual_seed()` reliably reproduces results *within* a consistent environment (confirmed directly here), but is not a guarantee of bit-identical CPU floating-point results *across* different sessions/machines -- a well-documented PyTorch limitation (thread-count-dependent reduction order in CPU matmul/BLAS operations), not a bug in this project's code. **Consequence, stated plainly**: the original "seed 4 never plateaus" finding was real when it happened, but this environment cannot reproduce that exact trajectory to test the patience hypothesis against it specifically -- the seed-4-focused version of this question is honestly untestable here, a genuine limit on how far seed-based reproducibility claims can be trusted across sessions, not something to paper over.

**Does removing time-series augmentation change the Transformer's real result?** `train_transformer.py --no-augment` (a flag that already existed but had never actually been run) trains fresh with `augment_batch()` disabled, otherwise identical hyperparameters. **A real, second bug was caught before it caused damage**: `--no-augment` had no distinct tag suffix (unlike `--shuffle-order`), so running it as originally written would have silently overwritten `dr_transformer_imu_norm.pth` -- the actual production Transformer checkpoint every other number in this report is built on. Caught and the run stopped within seconds of launch (confirmed via file timestamps that the production checkpoint was never touched), fixed by building a composite tag suffix (`_noaugment`, `_shuffled`, or both) from the CLI flags before training starts, relaunched safely. Windowed val loss without augmentation: 0.2212, far better than the with-augmentation model's 0.3545. The chained-trajectory result, the one that actually matters: **6.47 m final / 4.23 m mean** -- nearly half the with-augmentation Transformer's 12.46 m / 9.75 m, and the best single-run Transformer result anywhere in this project's history, better than every one of the 5 `cpu_5seeds` seeds individually. **The same honest caveat as the shuffle finding applies with equal force**: this is one no-augment run against one with-augmentation run, and the Transformer's 71% seed-to-seed CV means a single favorable run is not distinguishable from genuine improvement without the same multi-seed treatment. Augmentation was included in the original design from the start specifically to mitigate the data-diversity risk flagged in §19's own data-sufficiency check (never isolated until now, per §19.3's own admission) -- this result is the first direct evidence it may be net-harmful rather than helpful for this architecture on this data, a real, actionable finding, but not yet a confirmed one.

**The multi-seed confirmation was run, and this time the exciting single-run number did not hold up.** `ai_backend/train_transformer_multiseed_confirmation.py` trained the same 5 seeds without augmentation. Per-seed final error: 9.51 / 10.32 / 10.50 / 15.32 / 5.76 m -- **mean 10.28 m, 95% CI [6.05, 14.52] m**, against the real, with-augmentation Transformer's 9.10 m mean, CI [2.61, 15.60] m. The intervals overlap heavily: **removing augmentation is not a statistically defensible improvement**, and its mean is nominally slightly *worse* than the real Transformer's, the opposite of what the single lucky run (6.47 m) suggested. One genuine, secondary finding survives: the no-augment variant is meaningfully more consistent seed-to-seed (CV ≈ 41%, margin/mean) than the real Transformer's 71%, though not by enough to translate into a better mean. The honest conclusion, stated plainly: neither shuffling the input order nor removing augmentation moves the needle on the Transformer's reliability problem once tested properly -- of everything tried in this section (ensembling, two-phase uncertainty training, order-shuffling, removing augmentation), only ensembling (§19.10 above) produced a real, defensible improvement, and only as a mitigation, not a fix. More diverse training data remains the one genuine, un-run candidate fix, exactly as flagged from the start.

### 19.11 Track C delivered: wiring the RL policy into the live recovery hierarchy

§19.9 named this the one unstarted gap left in the live hierarchy: "RL still does not consume the orchestrator's output." Reason for the work: `recovery_orchestrator.py::_apply_seek_bias()` had, since §18, been a hand-coded proportional controller (`seek = direction/dist * min(SEEK_KP*dist, SEEK_MAX_CONTRIB)`) -- reasonable, but structurally blind to how much the estimate feeding it should be trusted, deciding on a full-strength correction identically whether the position estimate was fresh or badly drifted. The user asked to fix this, prioritized ahead of the data-diversity work below.

**Method.** `ai_backend/models/rl_path_recovery.py`'s old `SwarmRecoveryEnv` (a disconnected toy: degree-scale lat/lon, a fixed never-varying target, no uncertainty modeling) was replaced outright with `RecoveryPolicyEnv`, single-drone scope. The core design mechanism: the environment tracks a hidden `true_pos` (reward-relevant) separately from an agent-visible `believed_pos = true_pos + est_error`, an accumulating random walk -- forcing the policy to learn *when to discount its own observation*, something no memoryless function of `(believed_pos, goal_pos)` (i.e. the existing hand-coded formula) can ever do. Drift-sigma was calibrated from this project's own real chained-trajectory numbers (LSTM 26.34 m / EKF 132.5 m over the standard 125-step/12.5s segment), domain-randomized log-uniform per episode so the policy sees both estimator qualities in training. `ai_backend/train_rl_recovery.py` trains via Stable-Baselines3 PPO; `RecoveryOrchestrator` gained `use_rl_seek`/`set_navigation_policy()` (mirroring `set_model()`'s exact in-place-swap contract, so switching navigation policy mid-flight cannot silently discard `home_pos`/`rtl_active`/EKF state, the same bug class §19.8 fixed for model switching). A real, previously-latent bug was found and fixed while wiring the confidence signal through: `st.ekf.predict()` had only ever run on EKF-active ticks, so its covariance went stale on LSTM-active ticks -- exactly when the new confidence-aware seek term needs it most. A second real methodological problem was found and fixed: `eval_metrics.py`'s historic "100% vs. 28%" RL-vs-rule-based comparison, re-read in full while wiring this up, turned out to compare two independent, mutually disconnected toy simulations, neither of which had ever touched the real system's own `_apply_seek_bias` formula -- rebuilt to route both methods through the real formula and the same `RecoveryPolicyEnv` instance.

**Three environment-calibration bugs were caught before committing to the real training run**, each found by watching the hand-coded formula's own success rate in the new environment rather than assumed away: (1) the initial goal-distance range (10-150 m) was geometrically unreachable at the seek term's own 1.5 m/s speed cap within one episode, cut to 5-15 m; (2) `MAX_EPISODE_STEPS` was originally 300 (30 s), letting simulated belief-drift run nearly 4x past the real system's own `RTL_TIMEOUT_S=8s` give-up boundary -- fixed to exactly `RTL_TIMEOUT_S/DT`, since the real system would already have abandoned the goal and switched to RTL well before that; (3) the drift-sigma calibration itself had a units bug -- `evaluate_trajectory.py::euclidean_error()` is a *vector*-magnitude error (`np.linalg.norm(pred-gt, axis=1)`), but the original derivation used it as a *per-axis* sigma, inflating simulated 3-axis drift by ~1.73x (`sqrt(3)`, the isotropic-vector-vs-per-axis RMS ratio). Fixed by dividing the per-axis sigma by `sqrt(3)`.

**Result: real 10K-step PPO training** (`ppo_recovery_seek.zip`, budget matched to the original prototype's scale per the user's own "500K-1M seems too much, unnecessary" call). Honest outcome, not oversold: raw arrival success rate came in *lower* than the hand-coded formula's (2.0% vs. 9.0%), but RL learned to command corrections roughly 6-14x smaller across the board (0.10-0.25 m/s vs. the formula's 1.3-1.5 m/s, n>1500 steps/bin) -- a real, large-sample-verified behavioral difference, not noise, and not RL simply mimicking the formula at lower gain. A controlled acceptance test (`recovery_orchestrator.py`'s own smoke test, Test 10 -- fixed a real labeling bug in the process, `low_conf`/`high_conf` variables had the uncertainty-vs-confidence direction backwards) isolates confidence as the *only* varying input and confirms the intended mechanism is genuinely present: `‖seek‖` shrinks from 0.116 to 0.093 m/s as injected uncertainty rises from 0.3 m to 9.0 m. That same directional effect is *not* visible in naturalistic rollout statistics, where confidence, distance-to-goal, and elapsed episode time all grow together, and the stronger correlated effect of those masks the weaker, but real, causal confidence effect. Reported as what it is: the mechanism works, demonstrated in isolation; the training budget was not enough for it to dominate naturalistic behavior yet. `--rl-seek` is wired into `live_mission_demo.py` (with a `CheckButtons` toggle) and `udp_server.py`; `ml_pipeline.py`'s own third, independent copy of the RL-vs-rule-based comparison was refactored to call the now-real `eval_metrics.py` instead of reimplementing it a third time.

### 19.12 The un-run "more diverse training data" experiment, finally run

§19.9 and §19.10 both named this the one genuine, un-run candidate fix for the Transformer's reliability problem, after ensembling, two-phase uncertainty training, order-shuffling, and augmentation-removal were all tested and found wanting (§19.10). Reason for the work, scoped to what "more diverse data" could concretely mean without new flight recordings: `datasets/px4_raw/SOURCE.md` already documented an exact, never-executed next step from the original 6-log pull -- filter by `flight_modes` to bias toward real translational-dynamics flights instead of the original batch's bench/hover-style sample.

**Method, part 1 -- re-pull a larger, Mission-filtered batch.** `ai_backend/data_processing/download_px4_logs.py` reimplements the `dbinfo`/`download` API directly (no `download_logs.py` tool is vendored in this repo). **A real, previously-undetected error in this file's own SOURCE.md was found and fixed**: `flight_modes` was assumed to be a string field (`"Mission"`); a live `dbinfo` response shows it is actually a list of PX4 nav_state *integer* codes (e.g. `[2]`). The correct id-to-name mapping (`Mission = 3`) was taken verbatim from PX4/flight_review's own `app/plot_app/config_tables.py`, the same upstream tool this project's download logic already credits, not independently guessed. 40 additional Mission-filtered logs were pulled (46 total, 992 MB; 4 fail to parse with a `.ulg` message-format edge case, not investigated further, the other 42 load fine).

**Result, part 1**: re-running the exact same `train.py --sources px4` code path on the larger corpus took val loss from **~1.5 ("worse than predicting the mean," the original finding) to 0.2768** -- confirms this was a data-quantity/diversity problem, not a structural one, exactly as originally predicted but never tested until now.

**Method, part 2 -- physically-motivated synthetic diversity**, a different category from the augmentation already tested and found not to survive confirmation (§19.10's `--no-augment` result): every value either transform below produces was actually measured by a real autopilot at some point, not synthetic per-sample noise. `ai_backend/data_processing/px4_synthetic_augment.py::rotate_augment()` reframes a whole real flight as if flown at a different absolute heading -- body-frame quantities (accel, gyro, roll, pitch, speed, dt) are physically invariant under a pure world-frame yaw relabeling and are left untouched; only `delta_lat`/`delta_lon` and yaw are rotated together, keeping every row internally consistent (magnetometer is a known, deliberately undone simplification -- see the module's own docstring for why correctly rotating it risks a subtler error than the one this avoids, in the same spirit as this file's §19.1 gyro-unit caution). `::splice_augment()` builds new synthetic flights by joining one real flight's tail to another's head at a state-matched cut point (nearest neighbor in `[speed, roll, pitch, sin(yaw), cos(yaw)]`, gated by a distance threshold so a poor match is skipped rather than spliced anyway). A real val-set-leakage risk was found and fixed before any training ran: `create_dead_reckoning_dataset()`'s default row-sequential 80/20 split would, once augmented rows are concatenated on, put newly-added synthetic rows in the validation tail instead of real held-out data -- fixed by adding a `held_out_val_df` parameter so both arms validate against the identical, fixed, real-only rows.

**Result, part 2** (`ai_backend/train_px4_synthetic.py`, 3 seeds, matching this project's own established multi-seed rigor rather than trusting one run): baseline (real-only) mean val loss 0.2741, 95% CI [0.2657, 0.2824]; augmented (real + rotation + splice) mean 0.2587, 95% CI [0.2182, 0.2991] -- a ~5.6% better point estimate, and 2 of 3 augmented seeds beat every baseline seed outright (full curves in `runs/px4_synthetic_diversity/figures/`). ## 20. Track B Delivered: Swarm Connectivity Graph Prediction + Live Multi-Drone Demo

§19.9/§19.12 named Track B (swarm connectivity graph) as the one item scoped from the start but never started, per the user's own explicit "single drone first, address graph/swarm work last" prioritization. That single-drone rigor is now behind this project (§19.1-§19.13), and the user asked to build Track B for real this session: a genuine ML task, not a redundant deterministic graph computation, mirroring the exact three-method structure (handcrafted features / Node2Vec / GCN-GIN) from the user's own MSc Graph & Network Analysis coursework (`GNA-ΤΣΙΛΙΜΠΩΚΟΣ-25118`), reusing this project's own already-validated GPS-loss drift model rather than inventing an unrelated synthetic setup.

### 20.1 The task, designed to be non-trivial

Framing purely as "count the current graph's connected components" would be a deterministic `networkx` one-liner, not a real ML problem. Instead: **given** a snapshot of N drones' BELIEVED positions (each drone's own dead-reckoning estimate, corrupted by accumulated GPS-loss drift, reusing `models/rl_path_recovery.py`'s own `DRIFT_SIGMA_LOW/HIGH`, `RTL_TIMEOUT_S`, `DT` constants unchanged), **predict** whether the network will fragment (some drone loses every relay path back to a fixed base station) `K_SECONDS` later, once TRUE positions (unknown to the system) evolve under each drone's real velocity. The believed/true divergence, driven by each drone's own accumulated uncertainty, is what makes this genuinely predictive rather than a recomputation of the input.

### 20.2 Method, part 1 - synthetic dataset generator

`ai_backend/data_processing/swarm_network_generator.py`: N=6-10 drones + 1 base station per scenario, `AREA_SIZE_M=600`, edges = in-range pairs (mirrors `api/swarm_logic.py::SwarmInterlink`'s own relay-connectivity rule, adapted from lat/lon+haversine to local metres for consistency with every other model in this project). **A real calibration bug was caught before trusting the dataset**, the same "verify, don't assume" discipline as §19's own environment-calibration checks: an initial `COMM_RANGE_M=180` guess produced a 93.4% degenerate fragmentation rate (average node degree too low for the random-geometric-graph connectivity threshold at 6-10 drones), caught by the script's own sanity assertion (`0.10 < frac_frag < 0.90`), not discovered downstream. Fixed via a direct empirical sweep (200-280 m tested), landing on `COMM_RANGE_M=250` (confirmed stable ≈50% fragmentation across 4 seeds). Final dataset: 700/150/150 train/val/test scenarios, fragmentation rates 0.516/0.373/0.513.

### 20.3 Method, part 2 - three training methods, 3 seeds each

`ai_backend/train_swarm_connectivity.py`, mirroring the GNA notebook's own code shape (adapted from ENZYMES molecule classification to this graph's own node features: position, velocity, uncertainty, elapsed-loss-time), `confidence_interval()`/`set_global_seed()` reused verbatim from `train_px4_synthetic.py`:
- **Method A**: handcrafted `networkx` graph features (degree stats, density, clustering/transitivity, connected components, LCC diameter/avg-shortest-path, degree assortativity, betweenness/closeness centrality, plus base-station-specific centrality and the task's own physical aggregates: mean/std uncertainty, mean/std speed) -> `MLPClassifier`.
- **Method B**: hand-rolled biased-random-walk Node2Vec (own implementation, not the `node2vec` package, matching the coursework's) -> `gensim` skip-gram Word2Vec -> mean+max-pooled graph embedding -> `MLPClassifier`.
- **Method C**: PyTorch Geometric `GCNConv`/`GINConv` classifiers (`BatchNorm1d`, dropout, global mean/add pooling, GIN with jumping-knowledge concat-of-all-layers), trained end-to-end.

**Result** (test Macro-F1, mean and 95% CI across 3 seeds): Method A **0.841** [0.831, 0.852]; Method B (Node2Vec) 0.780 [0.629, 0.932]; Method C (GCN) 0.722 [0.674, 0.770]; Method C (GIN) 0.789 [0.725, 0.852]. Method A wins outright and with the tightest interval, plausible rather than surprising given these are small graphs (7-11 nodes): engineered topological features are a strong, low-variance baseline at this scale, and GNNs typically need substantially more graphs/nodes than this synthetic set provides to earn their extra capacity. Reported as the honest result, not adjusted toward a more "interesting" expected outcome. Full figures/confusion matrices: `runs/swarm_connectivity/figures/`; the best (highest-val-F1) Method A model is persisted to `runs/swarm_connectivity/method_a_model.pkl` for reuse in the live demo below.

### 20.4 Method, part 3 - live multi-drone simulation and real-time risk inference

`ai_backend/live_swarm_demo.py`, mirroring `live_mission_demo.py`'s own self-contained-demo pattern (matplotlib dashboard + `--headless-test`, no Godot required): 8 drones + base station, per-drone believed-position drift integrated tick-by-tick, a true random walk whose cumulative variance matches the offline generator's own formula, so live inputs stay in-distribution for the trained model, under a live GPS-loss toggle (per-drone or all-at-once). Every tick, the persisted Method A model scores the current believed topology for fragmentation risk via `extract_graph_features()` imported directly from `train_swarm_connectivity.py`, not reimplemented: a genuine live inference loop, not a canned animation. Seeded `--headless-test` (seed=3, checked directly to produce a clean fragmentation event): risk rises from 0.227 (GPS healthy) to 0.506 after 12s of sustained all-drone GPS loss, and the network genuinely fragments, asserted rather than eyeballed. Two screenshots captured for thesis use: `runs/live_swarm_demo_test_healthy.png` (all-green, low risk) and `runs/live_swarm_demo_test_fragmented.png` (one drone unreachable from base, medium/high risk).
